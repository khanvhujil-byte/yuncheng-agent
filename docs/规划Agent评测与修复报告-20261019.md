### 2.2 覆盖维度

- 城市 20+：杭州、北京、上海、成都、西安、三亚、丽江、苏州、广州、厦门、南京、重庆、青岛、哈尔滨、昆明、拉萨、乌鲁木齐、桂林、敦煌、杭州带后缀等；
- 天数 1 / 2 / 3 / 4 / 5 / 6 / 10 / 30；
- 交通 4 种 + 非法值（潜水艇）；住宿 4 种 + 民宿；偏好 0 / 1 / 2 / 多 / 重复 / 20 个；
- 必去景点 0 / 1 / 3 / 超容量 / 超 10 个 / 垃圾名 / 通名歧义；
- 固定酒店：正常 / 搜不到 / 跨城 / 重名 / 带地址消歧；
- 预算：无上限 / 低预算 300 / 800 / 1500 / 5000 / 100 万；
- 天气：窗口内 / 超窗 1/2/4/6 天 / 出发日在窗口外 / 过去日期 / 未来 30 天；
- 输入：空字段 / 非法日期 / 日期与天数冲突 / nights 越界 / nights=0 指定酒店 / 未知顶层字段 / 超长 city / 超长 free_text / emoji / SQL 注入样式 / prompt 注入；
- requirements 结构化字段：unverified、排除名单、max_per_day、max_day_minutes、max_price_per_night 等。

### 2.3 判定方式（不靠人眼看行程）

每个用例除声明期望外，统一检查跨用例不变量：

1. `len(days) == travel_days`、日期连续、`day_index` 连续；
2. 景点不跨天重复、每天 ≤4 个、每天有且仅有三餐；
3. 预算等式：`total = known_total + estimated_total = 四项分类和 = Σ day_total_cost`；`unknown` 项金额必须为 None 且不计入 total；
4. 住宿：`hotel_nights == nights`、`total_hotels == 单价 × 晚数`、nights=0 不得有酒店；
5. 天气：超窗口项必须留空（编造数必须为 0）、日期对齐、条数与天数一致；
6. 必去对账：`constraint_report.satisfied` 必须真的出现在 days 里、required 不得缺失、success 时 unsatisfied 必须为空；
7. success 语义：success=True 要求无降级 sources、无 validate_error、预算未超限；
8. 时间表可对账：总时长 = 时间表之和、交通时长 = route_legs 之和、无重叠/缺口、午餐不晚于 14:00、晚餐不晚于 20:30、总时长不超过 660 分钟；
9. 来源枚举合法、无占位式假名（景点1/酒店1 等）、响应可 JSON 序列化。

基线暴露出一个系统性事实：**同一个失败模式会重复出现在多个城市/天数上**。例如 4 条 3 天行程全部因"660 分钟舒适度无法修复"失败（G01-G04），说明不是模型偶发，而是缺少确定性兜底。

## 4. 发现并修复的问题

严重度定义：P0 = 违反硬约束仍 success=True（本轮未发现）；P1 = 用户可见的错误结果/假成功/主要失败模式；P2 = 健壮性、可观测性、运维风险。

### 4.1 规划核心

| 编号 | 问题 | 证据 | 修复 |
|---|---|---|---|
| P1 | 统一编排模式下没有任何确定性舒适度修复：模型重试耗尽后仍交付 660 分钟以上的不可执行行程（`success=false` 但 data 仍含 709/811/957 分钟的天） | 基线 G01-G04；`itinerary_experience.py` 中 `can_reduce()` 对 unified 恒 False | 新增 `can_trim()` 与 `trim_overfull`：按审计后的时钟确定性删**可选**景点（required/锚点/用户编辑餐次受保护），最多 3 轮；删除后按估算重建时钟，避免过度删点；允许 17:30/17:00 提前晚餐压低固定餐窗带来的地板时长 |
| P1 | 模型把同一景点排到两天：verify_plan 判严重 → 重试用尽 → 交付重复行程 | 基线 G02（西湖出现在第 1、3 天） | compose 后确定性地保留首次出现；若某天只有重复景点，用未使用候选替换；无候选才保留并写明原因 |
| P1 | 模型输出非法 JSON 直接吃掉一次语义重试名额；长行程还常因输出被截断而失败 | 基线 8 例 MODEL_JSON；G06/G13/G14/G17 等 | ① 编排输出 token 预算按天数自适应（最长 8192）；② 同一节点内做一次"格式修复"重试，不消耗语义重试；可用 `PLANNER_FORMAT_RETRY_ENABLED` 关闭做对照 |
| P1 | 删点修复本身把 2 个景点就能满足的一天删到只剩 1 个（while 读旧时间表） | 静态审计 P1-2；复现脚本 `probe_trim_repo_case.py` | while 每删一次都用 `simulate` 重算估算总时长，达标即停；外层 3 轮只在真实时钟仍超时后继续 |
| P1 | `prepare_planning_context` 漏返回 `sources`，食品补搜成功后仍按 `catalog_partial` 判降级（假降级） | 静态审计 P1-4；数据已补齐但 success=false | 节点返回 `sources=state["sources"]`，与 enrich 节点的做法一致 |
| P1 | comfort 修复与预算重排共用 `budget_retries`，体验修复会吃光预算重排名额 | 静态审计 P1-5 | 拆分 `repair_rounds` 与 `budget_retries`；新增 `prepare_repair` 节点，两类重排各自封顶 2 轮 |
| P1 | compose 的 LLM 错误路径写 `plan=_empty_plan`，重排轮里会把上一版已生成行程顶掉 | 静态审计 P1-6 | LLM 错误路径不再写 `plan`，保留上一版；错误只写 warnings/errors |
| P1 | `audit_choices` 在餐饮候选缺失时对 `restaurant_id` 直接下标，抛 KeyError 让整条已生成行程变异常 | 新单测构造 restaurants=[] 时复现 | 改为 `.get`，显式给出"缺少已核验餐厅"错误；`correction_context` 同样修复 |
| P2 | verify_plan 的"回喂重试"注释与实际实现不一致 | 静态审计 P1-1 | 不强行改成模型重试（会多烧调用），而是把契约改为：enrich 确定性修复 → 复审 → 仍有问题再进入有界 repair，并同步注释 |
| P2 | 餐饮距离规则把"附近根本没有 4km 内候选"也当硬错误，导致数据覆盖差的城市必然失败 | 基线 G05/G07/G11/G18/G19 | 有更近候选时仍报错并确定性换店；没有更近候选时降级为 warning（"保留当前餐厅，约 X 公里"），不再把数据覆盖问题判成行程失败 |

### 4.2 HTTP / 缓存 / 数据层

| 编号 | 问题 | 证据 | 修复 |
|---|---|---|---|
| P1 | 缓存命中后复核失败，坏条目继续被命中且 hit_count 照涨 | 静态审计 P1-1，已用脚本复现 | 复核失败且为"行程内在问题"（有 days、无降级、有未解决项）时删除缓存条目；瞬态降级（天气/价格源）不误删 |
| P1 | 进程重启后遗留 `job_state=running` 永不回收：`/plan/result` 永远"仍在生成中"，SSE 永不结束 | 静态审计 P1-2，已复现 | 启动时 `store.mark_stale_jobs()` 把 running 标记为 error；`get_job` 仍可读结果或给出明确错误 |
| P1 | 请求字段无长度/数量上限：可传 MB 级 city/free_text 进 prompt、指纹与数据库 | 静态审计 P1-4，实测 2MB 被接受 | `TripRequest` 增加上限（city 100、free_text 20000、preferences 20、must_visit 20、酒店/地址 200/300 等）；超限 422 |
| P1 | 生成完成后写行程库无异常隔离，SQLite 一繁忙就把已花成本的行程变 500 | 静态审计 P1-5 | `save_itinerary` 外包 try/except，失败降级为 warning；`find_itinerary` 内部捕获 DB 异常按未命中处理 |
| P1 | 监控把预检/输入拒绝算成"规划失败"，健康服务也常亮 PLAN_FAILURE_RATE | 静态审计 P1-6；真实库 plan_success_rate=0.0645 | 预检类错误码单独计数，`plan_success_rate` 只在真正进入生成流程的请求上计算 |
| P2 | 异步接口命中缓存时先返回 success=True，与复核结论可能矛盾 | 静态审计 P2-1 | 返回 `response.success` 与原因 |
| P2 | 预检失败用户文案是通用的，不知道是哪个景点/酒店有问题 | eval-scout 发现；G25/G32 实测 | 把 `state.errors` 里的具体原因附到 message |
| P2 | CLARIFICATION_REQUIRED 没有专属文案 | eval-scout 发现 | 增加专属提示 |

### 5.2 HTTP 契约

`backend/scripts/eval_http_contract.py`：**44/44 PASS**，覆盖：

- 基础端点：health / metrics / 404 / 405；
- 输入校验：坏 JSON / 缺字段 / 越界字段 / 未知字段 / 超长 city / 超长 free_text / emoji / SQL 注入样式 / prompt 注入；
- 同步预检契约：HTTP 200 + success=false + error_code + data=null；

## 6. 剩余风险与未修项（诚实清单）

1. **长行程 JSON 截断**（G13 10 天、G17 30 天）：已把输出预算提到 8192 并加一次格式修复，但仍可能两次都非法。根治需要分天生成或 JSON schema 约束解码，属于下一轮工作。
2. **餐饮/酒店数据覆盖**：G05/G07/G19 所在片区 AMap 候选不足，规划器没有可换的近邻餐厅；当前如实返回部分结果 + warning。改善需要资料库预热/更多候选来源，不是模型或校验代码能修。
3. **舒适度地板**：G26 敦煌删到最少仍 776 分钟（真实路线长 + 固定餐窗）。系统已确定性删点后仍诚实失败，但用户看到的是部分结果；下一步应在选点前就用真实路程做可行性预筛。
4. **锚点名歧义**：短名（如"西湖""象鼻山""武侯祠"）会返回 `ATTRACTION_AMBIGUOUS`，现在 message 会带具体名字，但没有候选列表供选择。
5. **静态审计确认的 P2**：全部超窗口时 `sources.weather="amap"` 与内容不一致；顶层未知字段被静默忽略（建议 `extra=forbid` 或 warning）；`partial_edit` 新 thread_id 未登记；同形请求并发无 in-flight 合并；`/api/ai` 无鉴权；同步线程池饥饿（40 并发慢请求可拖死 /health）；Docker 镜像未实机验证；Java 侧仍用占位身份与进程内队列。
6. **样本与随机性**：每个场景只跑 1 次，模型温度 0 但仍有波动；JSON 失败类用例具有随机性，82% 应视为单次观测而非稳定下界。
