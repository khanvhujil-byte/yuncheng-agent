## 简历条目（三条，可直接贴简历）

1. **多智能体架构**：基于 LangGraph 实现多智能体旅行规划服务，含 4 个专职 Agent（景点搜集 / 天气 / 住宿 / 行程编排）与 6 个工具；把去重、类目过滤、预报窗口对齐、加权选址等确定性规则**下沉到工具层**，Agent 只负责决策——规则因此可单测，Agent 保持自主。

## Q1 · 为什么用多智能体，而不是一个 Agent？多智能体的代价是什么？

**这题在考什么**：你是不是因为"多智能体"这个词好听才这么做的；有没有成本意识；知不知道什么时候**不该**拆。

**30 秒版**：

我拆了四个专职角色——景点搜集、天气、住宿、行程编排，各自带自己的工具，用 LangGraph 按固定流程编排起来。拆的理由是这几件事的输入输出和失败方式都不一样：搜景点要处理重复和类目过滤，天气要处理预报窗口，住宿要做距离权衡，编排是纯生成。代价我实测过：单次 3 天规划平均 10.5 次 LLM 调用、约 1.8 万 token、41.9 秒中位数。所以我的结论是"该拆才拆"，不是越多越好。

**追问弹药**：

- 判断标准三条：步骤数会不会变 / 工具选择有没有歧义 / 失败要不要自主换策略。**有一条是"是"，才值得上 Agent**。
- Agent 化代价对照（真跑，每臂 3 次取中位数）：全 Agent **43.6 秒 / 11 次调用 / 18,034 token**；把天气换回纯工具 **44.7 秒 / 9 次调用 / 16,925 token** → 省 token，但**延迟没降**。
- 原因：天气节点在**并行分支**上，去掉它不缩短关键路径。**只有关键路径上的 Agent 才会拉长端到端时间。**
- 单个采集 Agent 约 2 次 LLM 调用 / 1300 token / 9 秒（3 个偏好标签触发 3 次工具调用）。
- 反面我也能说清：如果只有一个数据源、流程固定不变，那一个节点就够，多拆只是多花钱多出错。

## Q2 · 为什么把去重 / 过滤 / 窗口对齐 / 选址数学放在"工具层"，而不是 prompt 里？

**这题在考什么**：是否理解「prompt 是建议，代码是保证」；以及你到底是"编排 LLM"还是"写工程"。

**30 秒版**：

因为写进 prompt 的规则是**建议**，遵守率会掉；写进工具里的规则是**代码**，必然执行。所以分工是：Agent 只负责决策——搜哪些关键词、够不够、选哪家酒店；工具负责正确执行——按 poi_id 去重、排除餐饮住宿类目、把 4 天预报窗口和行程日期对齐、算加权选址。这样既拿到多智能体的自主性，又没丢确定性。

**追问弹药**：

- 实测反例：prompt 里写了"每天安排 2~3 个景点"，模型照样排到 5 个，所以我加了第 1 层校验兜住。
- 收益：规则进了工具之后**变得可单测**（Agent 不好测，工具好测）。
- **收集箱机制**：工具把结构化数据写进上下文对象，只把摘要回填给模型（"返回 20 条，采纳 19 条，累计 57 条"）——省 token、不丢数据、数据不经过模型的手就不可能被编造。
- 取舍例子：我试过白名单（只留风景名胜 / 科教文化类），结果"河坊街"（typecode 是 190301 道路名）被误杀，所以最终按需求只排餐饮（05）和住宿（10）。
- 六个工具：`search_attractions` / `get_weather` / `search_hotels` / `rank_hotels` / `measure_distance` / `choose_hotel`；工具带**角色权限**——天气 Agent 调不了 `choose_hotel`。
- 连"决定"也走工具：选酒店用 `choose_hotel` 落进收集箱，而不是让模型写在自然语言里再被解析。

## Q3 · 为什么预检要放在花钱之前？你拦住了哪些东西？

**这题在考什么**：成本意识 + 边界意识。面试官想听"你能不能在花掉钱之前发现不该花"。

**30 秒版**：

因为跑完 40 秒、烧掉一万八千 token 才告诉用户"你的必去景点装不下"，是最差的体验。所以我把可行的检查全放在最前面，而且这个预检节点**一次模型都不调用**——不通过就直接返回明确的错误码。

**追问弹药**：

- 拦住四类：日期与天数对不上、晚数越界、必去景点数量超过容量（天数 × 3）、城市解析不出来。
- 还拦高德的确定性错误（Key 无效 / 配额用尽 / 参数错误），不让它**静默降级**成"这座城市没景点"。
- 有一类**不拦但提前告知**：行程超过 4 天必然超出高德预报窗口，预检阶段就记下来。
- 失败给的是可用信息，不是"服务器错误"：比如 `CONSTRAINT_INFEASIBLE`，前端会说"请减少景点或增加天数"。
- 实测整体：21 次运行里**降级 0 次、约束满足 21/21**。

## Q4 · 两层校验分别是什么？为什么要回喂重试？重试封顶后怎么办？

**这题在考什么**：结构化输出的工程能力——你怎么让模型"必须按形状交付"。

**30 秒版**：

第 1 层是**结构校验**：JSON 能不能解析、天数是否等于 `travel_days`、日期是否连续、每天景点数有没有超上限。第 2 层是**业务约束校验**：用户必去的景点是不是真的排进了行程、有没有编造候选池之外的景点。不通过就把"具体哪里错"回喂给模型重试，最多 2 次。

**追问弹药**：

- 为什么必须回喂：不说清哪儿错，模型只会重犯；说清"第 3 天的日期应该是 10-12，你写成了 10-13"，它一次就改对。
- 封顶之后**不丢弃请求**，而是继续往下走，把未满足项如实写进约束对账报告（`unsatisfied` + 每条原因）——这就是"降级不静默"。
- 那个错误字段一物两用：**既是回喂内容，也是条件边的开关**，因为它俩本来就是同一件事。
- 实测：21 次运行约束满足 21/21；期间确实触发过重试（日志里能看到"安排了 5 个景点，超过每天上限 4 个"）。
- 编排之后还有一步**回填**：图片、评分、poi_id、"必去"标记都不让模型复述，按 poi_id 或名字从候选池补回去。

## Q5 · 你项目里的"诚实性"具体指什么？怎么验证的？

**这题在考什么**：你会不会只会说"我不让模型幻觉"——要的是**可验证**的说法。

**30 秒版**：

指三件事。第一，外部数据查不到就**留空**，不编造。第二，估算的数据必须**标出来源**（高德实查 / 模型估算 / 用户指定）。第三，降级和没满足的要求必须**让用户看见**，不许静默。验证方式是"可对账"：约束有对账报告，天气有超窗口标记，来源有来源字段。

**追问弹药**：

- 硬判据：**标记了"超出预报窗口"却填了天气内容 = 编造**，这个数代码能直接算，不需要人工抽检。21 次运行共 18 个"超窗口天次"，**编造 0 次**。
- 用户看得见：来源标签（预估 / 实查 / 你指定的）、降级警告、未满足条目和原因。
- 成功与否的判据也从"有没有警告"改成了"来源里有没有降级"——因为警告里混着说明类的话（比如"必去景点已解析为某某"），那种情况行程其实是完整的。
- 数据裁剪也是诚实性的一部分：单条 POI 从高德取回来 1604 字节，我裁到 583 字节（**省 64%**），原始响应不进任何上下文——不给自己"顺手编一句"的机会。

## Q6 · 为什么"天气不编造"这个点值得单独做实验？

**这题在考什么**：你能不能把一个质量要求变成**可测量的指标**。

**30 秒版**：

因为高德天气接口有硬上限——**只返回今天起 4 天**。行程一超过 4 天，就必然有一部分天没有数据。这不是我设计的场景，是外部数据的天然边界，正好拿来当实验的自变量：天数从 2 加到 8，看超出窗口的天有没有被如实留空。

**追问弹药**：

- 实验设计：天数 **2 / 4 / 6 / 8**；结果超窗口天数是 **0 / 0 / 2 / 4**，而**编造天数恒为 0**。
- 判据是代码算的（超窗口却填了内容），比"人工抽检 20 条"更硬、可复现。
- 产品上也有取舍：超窗口的那天我给一个**占位项**（日期留着、天气字段空、标 `beyond_window`），而不是干脆不输出——否则 6 天行程只显示 4 个格子，用户会以为天气功能坏了。
- 还要分清两种"没有天气"：**超出窗口（正常）** 和 **接口失败（故障）**；前者来源标记仍是高德，后者是降级。
- 这条能回答"你说降低幻觉，具体治的是哪一类"：治的就是"预报窗口外的天气编造"，而且有数字。

## Q7 · 缓存（行程库）的指纹为什么不含出发日期？命中后为什么还要重取天气？

**这题在考什么**：缓存设计的正确性——能不能分清"哪些可以复用、哪些绝对不能"。

**30 秒版**：

指纹不含日期，是因为同一批需求换个出发日期，**行程骨架完全可复用**——景点、顺序、三餐、酒店、预算都跟日期无关。但天气**不能**复用，它跟日期绑着，把 10 月 10 日的"晴 26 度"搬到 10 月 24 日，那就是编造。所以命中后我只做两件事：把日期整体平移、按新日期重取一次天气。

**追问弹药**：

- 实测：首次生成 45.2 秒；完全相同的请求 **3.7 秒**；**只改出发日期 2.4 秒**——日期平移到新日期后，天气三天**全部标记超窗口、如实留空**。
- 统计：生成平均 40.3 秒 vs 命中平均 **2.2 秒**（约 **18 倍**），命中时 **0 次 LLM 调用**（但要 2 次高德调用：地理编码 + 天气）。
- 指纹规范化：偏好标签和必去景点都**排序**（勾选顺序不同不算另一批需求）、字符串去空格。
- 用 sha256 而不是 Python 的 `hash()`：后者每次进程重启都会变，没法落盘复用。

## Q8 · 什么情况下你不缓存？

**这题在考什么**：知不知道"缓存也会固化错误"。

**30 秒版**：

只有**完整、且没有任何一路降级**的行程才入库。原因很简单：把一份降级结果缓存下来，等于把一次故障**永久固化**，之后每次命中都会返回缺数据的那一份。

**追问弹药**：

- 判定就是：`days` 非空，且来源标记里没有"降级"。
- 指纹里包含用户的自由文本要求，改一个字就算另一批需求，不会错误命中。
- 现在**没有淘汰策略**，这是已知短板——酒店和价格会随时间过时，正确做法是按"出行日期已过"清理，或加过期时间。
- 命中次数、命中率、命中与未命中各自的平均耗时都记在库里，可以直接查——"我加了缓存"这句话是可验证的。

## Q9 · 断点续跑的能力边界在哪？为什么不做全图续跑？

**这题在考什么**：你会不会**诚实**（这题最能筛出吹牛的人）。

**30 秒版**：

我只支持"**两路采集都完成之后**"的线性段续跑：从编排、从住宿、或从预算继续。更早的断点——比如城市都还没解析完——就老实从头跑。因为假装能续跑比不能续跑更糟。

**追问弹药**：

- 实现方式：每个节点的产出写进 journal 表；续跑时把历史碎片按 reducer 语义拼回一个状态，然后把图的入口从"解析城市"换成"第一个没做的节点"——**图的结构一行没改**。
- 实测：删掉住宿和预算两个节点的 journal 后，接口说可以"从住宿继续"，**22.8 秒**就出了完整行程。
- 为什么必须自己复刻 reducer：reducer 只在图内生效；从图外拼状态就得照抄一遍——列表追加、字典合并、数字累加、其余覆盖，这三个特例必须和状态定义保持一致。
- 后台任务表在**进程内存**里，后端一重启旧任务号就找不到了。这是单机项目的刻意取舍，要分布式就得上 Redis。
- 规划未来：先用 journal 把"最贵的编排"保住，这已经覆盖了大部分重跑成本。

## Q10 · SSE 逐节点进度带来了什么意外收获？

**这题在考什么**：你有没有真的从可观测性里拿到东西（不是"加了个进度条"就完了）。

**30 秒版**：

本来只是想让用户别干等 40 秒。结果它第一次把瓶颈照出来了——逐节点时间线显示**住宿 Agent 花了 98 秒**，而最贵的编排只有 18.7 秒。同步接口下你只会看到"总共 116 秒"，根本不知道是谁慢。

**追问弹药**：

- 根因：prompt 让它对**多家酒店逐一实测距离**，每家都是一轮模型调用加一次高德调用。
- 修法：prompt 改成只对排名第一的那家实测 1~2 个景点；步数上限从 6 收到 5 兜底。
- 效果：住宿那一步 **98.2 秒 → 13.1 秒**（优化后 10 次采样的中位数），端到端 **116.4 秒 → 31.1 秒**。（单次对比，住宿那步方差本来就不小，方向明确但还要多跑几次才算结论。）
- 技术手法：用图的双模式流同时拿 `updates` 和 `values`——`updates` 用来推进度、写 journal，`values` 用来拿完整状态组装响应；既不用自己实现合并逻辑，也不用改图。
- 前端做了**三级降级**：流式失败先转轮询，再失败才回到原来的同步接口；老路径原样保留，不会因为新功能坏掉。

## Q11 · 你的项目里哪些地方故意不用 LLM？为什么？

**这题在考什么**：有没有"能算的别让模型算"的直觉——这比"我会用 LLM"值钱。

**30 秒版**：

预算加总、日期推导、景点去重与类目过滤、天气预报窗口对齐、住宿的加权选址数学——这些全是代码；另外整个预检节点不调模型。理由是它们都有唯一正确答案，交给模型只会引入错误和成本，而且**算错很难被发现**。

**追问弹药**：

- 预算最好说：预算卡上写"总计 2060"，没人会真去逐项加一遍；住宿费必须是"单价 × 晚数"，不能按天求和（按天求和会多算一晚）。
- 编排之后的那步"回填"也是这个思路：图片、评分、"必去"标记不让模型复述，按 poi_id 从候选池补。
- 我也做过**反向实验**：把天气节点从 Agent 换回纯工具，省了 2 次调用和约 1100 token，但延迟没变——说明并行分支上的 Agent 化只花 token 不花时间。
- 但我也不是"能不用就不用"：搜景点用什么关键词、够不够、选哪家酒店，这些是判断，交给 Agent。
- 一句话总结自己的原则：**事实性判断问检索接口，模型只做"给定候选的排序与选择"。**

## Q12 · 你踩过最坑的一个 bug 是什么？

**这题在考什么**：调试能力 + 真实性。面试官在分辨你是真做过还是背过。

**30 秒版**：

最坑的是**住宿费莫名其妙算成 0**——酒店选出来了、单价也有，但总住宿费是 0。查下来是：我往状态里写了一个**没在状态定义里声明的字段**，而 LangGraph 对未声明的键是**直接丢弃**的，于是预算节点读到的晚数是 0，260 乘 0 等于 0。整个过程请求正常、日志无异常，**只有金额是错的**。

**追问弹药**：

- 为什么算"最坑"：它是**静默**的。没有报错、没有告警；如果不是我加了"每日小计之和必须等于总额"这种对账，根本发现不了。
- 修法两步：删掉那个多余字段（晚数只留一个真相源），并给预算加对账（改之前还差过 1 元，是取整导致的）。
- 另外三个值得讲的：
  - **规则用错场景**：相关性判定（逐字重叠 60%）被我误用到类目关键词搜索上，搜"自然风光"返回的 20 条**全被误杀**——同一个规则用在错误场景比不用更糟，而且它不报错。
  - **判据选错**：成功与否原来用"有没有警告"判断，导致一条"必去景点已解析为某某"的正常说明也会让整个响应变成"部分结果"；改成看来源里有没有降级。
  - **混合体序列化**：行程对象一部分是普通字典、一部分是 Pydantic 对象，入库时直接序列化会崩，而且崩在"行程已经生成完、时间和钱都花掉"的那一刻。
- 沉淀出的两条经验：**写进状态的每个键都必须声明**；**金额类字段必须有对账**。

## Q13 · 如果并发量上来，你的架构哪里会先崩？

**这题在考什么**：有没有系统观，还是只会做单机 demo。

**30 秒版**：

先说最脆的三处。第一，一次规划要 40 秒左右，而同步接口是阻塞的——并发一上来线程池会被占满，**最先崩的是这个接口**。第二，后台任务和会话状态都在**单进程内存**里，多开一个实例就查不到别人起的任务，重启也丢。第三，外部依赖有硬配额：高德接口每天有调用量上限，模型也有速率限制。

**追问弹药**：

- 已经有的缓解：异步提交 + SSE 把长连接从"占住请求"变成"推事件"；行程库缓存让同形状需求 2.2 秒返回、**0 次模型调用**；编排前做了上下文压缩，prompt 从 6097 字符降到 2645 字符（**省 57%**）。
- 改造顺序：先把任务状态和 journal 从内存搬到 Redis，再给高德和模型加统一限流与退避，最后才是多实例部署。
- 数据库现在是 SQLite，单机没问题；多实例写会锁冲突，要换 Postgres。
- 我不会假装现在是分布式的——代码注释里写明了"单机单用户够用"。

## Q14 · 这个项目的局限是什么？

**这题在考什么**：会不会**自己挑毛病**。这是面试官最看重的一题，答"没有局限"直接减分。

**30 秒版**：

我主动列四条。第一，**样本小**——每个实验条件只跑 3 次，而且只测了杭州一个城市，结论只能当趋势，不能当统计显著。第二，模型即便温度设 0 也**不是逐位可复现**，所以我用中位数而不是单次。第三，观测"酒店到景点"的距离用的是**球面直线距离**（为了不消耗接口配额），真实驾车距离只对最终选中的酒店测一次。第四，延迟里含外部服务抖动，同一天不同时段跑同一批条件结果会有差异。

**追问弹药**：

- 功能层面还有两个：行程库**没有淘汰策略**（酒店和价格会过时）；后台任务状态在单进程内存里，**重启即丢**。
- 住宿 Agent 的耗时方差很大，98 秒那次是异常值，目前只做了初步优化，要跑 10 次看 p50 / p95 才能定论。
- 上下文压缩只量化了 prompt 大小（省 57%），**对行程质量的影响还没测**。
- 我会在报告里写清采集时段和局限，而不是只报最好看的那次。

## Q15 · 如果让你重新做一遍，你会改什么？

**这题在考什么**：复盘能力，以及你有没有从踩坑里真正学到东西。

**30 秒版**：

三件事。第一，状态字段一开始就定"**能不加就不加**"，晚数只留一个真相源——那个"住宿费算成 0"的 bug 就是因为多加了一个字段。第二，从第一天就把**节点级进度和成本指标**（每次模型调用、每次工具调用）记下来，因为可观测性收益最大——住宿慢 98 秒是加了进度才看见的。第三，先做**结构性的省钱**（缓存、上下文压缩），再做功能：命中一次省 40 秒和一万八千 token，比优化任何单个 prompt 都值。

**追问弹药**：

- 顺序上更合理的是：契约 → 可观测性 → 关键路径性能 → 功能扩展。
- 我会更早把"工具层"抽出来，而不是先在节点里写规则再搬——搬运本身没出错，但规则散在两处的那段时间最难受。
- 我会更早给每个外部依赖写"可降级 + 可对账"的封装（高德那层做对了，后面四个接口都很省事）。
- 我会更早定"成功判据"：用来源降级标记，而不是"警告是否为空"。

## Q16 · 为什么住宿要放在行程编排之后？

**这题在考什么**：算法意识和设计一致性——是不是抄来的。

**30 秒版**：

因为选哪家酒店的**自变量是"实际会去哪些景点"**。候选池有几十个景点，其中一半不会去；如果用候选池选址，等于把不去的地方也算进距离，选出来的酒店会偏。所以顺序是：先排行程，再拿真实行程里的景点做加权选址。

**追问弹药**：

- 加权公式：把酒店到每个行程景点的距离，按该景点的**建议游览时长**加权取平均，选最小的那家——待得越久的景点，酒店离它近就越值钱。
- 排序用坐标算直线距离（不消耗配额），最终选定的那家再用距离接口**实测一次**真实驾车距离。
- 用户已经订好酒店时，这条路径退化成"解析并采用用户的酒店"，同时如实给出距离说明。
- 实测代价：用户指定一家看起来还行、但不是最优的酒店，加权平均距离 **4.3 公里**，而系统选址是 **2.2 公里**，差 95%。

## Q17 · 上下文压缩怎么做的？为什么不会漏掉必去景点？

**这题在考什么**：会不会为了省钱牺牲正确性。

**30 秒版**：

压缩只对送进编排的候选清单做预算裁剪：**必去锚点永远保留**，其余按高德评分降序，上限取"24 条 / 天数 × 4 / 锚点数"里最大的那个——也就是"**够用优先于省 token**"。而且在提示词里会如实告诉模型"候选池共 58 个，已筛出 24 个"。

**追问弹药**：

- 实测：同一候选池 58 条，关闭压缩时 prompt **6097 字符**，开启后 **2645 字符**，**省 57%**；锚点确认保留。
- 为什么不能压得更狠：编排每天要用 2~3 个景点，天数一多清单必须给够，否则模型无米下锅。
- 这是**可控开关**（配置项），方便做 A/B；目前只量化了 prompt 大小，质量影响还没测。
- 另一层压缩是"工具结果不进对话"：原始 POI 数据进收集箱，只把统计摘要回填给模型。

## Q18 · 你的对照实验怎么保证公平？

**这题在考什么**：实验素养——你是不是只挑好看的那次报。

**30 秒版**：

三条。第一，**同一个请求、同一批输入，只切一个开关**——比如天气节点走不走 Agent；两条路径调用同一个工具、产出完全一样的天气数据，所以对比是干净的。第二，**指标口径写死在文档里**，比如端到端延迟是进程内跑图的墙上时间，token 是四个 Agent 的累加值。第三，每个条件**跑 3 次取中位数**，因为模型即便温度 0 也不是确定的。

**追问弹药**：

- token 为什么要专门处理：默认行为是**覆盖**，那样只剩最后一个节点的用量，量不出总成本——所以我给用量字段加了累加逻辑。
- 必须**同时报质量列**：如果关掉天气 Agent 导致景点数或约束满足率下降，那就不叫"省了成本"，而是"漏了功能"。
- 观测指标事后用坐标算，不依赖任何 Agent 的自我报告。
- 21 次运行：约束满足 **21/21**、降级 **0/21**、编造天气 **0 次**。
- 局限也写在实验章里：样本小、单城市、直线距离近似、延迟含网络抖动。

## Q19 · 你怎么保证外部数据不被模型编造？

**这题在考什么**：对"让模型复述数据"这个风险的意识。

**30 秒版**：

一条原则：**模型不复述数据，字段由代码回填**。天气不让编排 Agent 抄一遍，直接在响应边界拼进去；景点的图片、评分、poi_id、"必去"标记都不让模型输出，按 poi_id 或名字从候选池补回来。**数据不经过模型的手，就不可能被编造。**

**追问弹药**：

- 实测教训：不回填的时候，行程里景点的首图**全丢**、"必去"标记**全丢**——因为模型根本没有义务复述这些字段。
- 工具层是同一套：搜到的原始数据进收集箱，回填给模型的只有统计摘要。
- 还有硬校验兜底：每天的景点必须来自候选清单，编造的直接触发重试。
- 三处一起用：**工具层不进对话 + 编排后回填 + 第 2 层校验查编造**。

## Q20 · 数据库为什么选 SQLite？够用吗？

**这题在考什么**：技术选型的合理性，别硬上重装备。

**30 秒版**：

因为这是单机单用户的求职项目：SQLite **零运维、零依赖、标准库直接能用**，还能把整个库文件拷走当证据。它存两类东西：行程（按需求指纹索引）和每次运行的指标日志。

**追问弹药**：

- 表结构：`itinerary`（指纹、城市、天数、原始请求、完整行程、建立时间、命中次数）、`run_log`（每次运行的耗时、模型调用次数、token、是否命中）、`graph_run` 与 `graph_journal`（后台任务与节点级产出）。
- 边界：单机写没问题；**多实例部署会因锁冲突出问题**，那时候要换 Postgres。
- 统计是直接 SQL 查的：命中率、命中与未命中的平均耗时、累计 token——这让"我加了缓存"变成可验证的数字（当前：命中率 33%、命中平均 2.2 秒、生成平均 40.3 秒）。
- 已知短板：没有淘汰策略，行程会随出行日期推移变旧。

### 高德接口的硬事实（实验设计的地基）

- 天气预报 `extensions=all` **只返回今天起 4 天**。
- POI 搜索对中文会**分词**，**几乎不返回 0 条**；`match` 字段恒为 `"0"`、`importance` 恒为空 → **没有可用的匹配度信号**，相关性必须自己判。
- `typecode` 可能是多个码用 `|` 拼接；05 = 餐饮、10 = 住宿、11 = 风景名胜、14 = 科教文化。

### 四个"真 bug"（面试讲这个最加分）

1. **未声明的状态键被框架静默丢弃** → 住宿费读到的晚数是 0 → 260 × 0 = 0；请求正常、日志无异常，只有金额错。
2. **规则用错场景**：逐字重叠 60% 的相关性判定被用到**类目关键词**搜索上 → 搜"自然风光"返回的 20 条全被误杀。
3. **判据选错**：成功与否从"有没有警告"改成"来源里有没有降级"。
4. **混合体序列化**：行程对象一半是字典、一半是 Pydantic 对象，入库时崩在"时间和钱都花掉"的那一刻。
