# 本地资料库与天气缓存

请求链路：城市校验 → 景点/天气/餐饮并行 → 行程编排 → 酒店选址 → 路线和体验校验 → 总预算与最终交付校验。新增本地检索位于采集工具内部，保留原图的依赖和局部修改流程。

## 已实现

- 景点、酒店、餐厅按城市、类型、来源和有效期存入 SQLite。名称、地址、来源类别、菜系建立中文词项倒排索引；自然风光等偏好按明确的来源分类别名检索。
- 在线搜索先查本地，重新匹配旅行日期对应的价格证据，再执行排除项和价格上限检查。有效候选不足、关键词缺失时才补查上游，保留原有次数和时间预算。
- 当前候选阈值：景点每次2至6个（受请求limit限制），酒店3个，餐厅4至12个；是可配置代码策略，不是召回率或城市覆盖承诺。长行程和稀有条件仍可能不足，保留警告和最终校验。
- 未知价格仍为未知。POI入库不产生房价、房态、门票报价或无障碍证明；模型酒店估价、晚数和距离不作为共享事实保存。只有日期适用且未过期的价格观察参与价格硬约束。
- 本地读取、行程保存和索引迁移都不会刷新原观察时间。只有真正线上采集才续期；历史导入支持原采集时间，旧观察不能覆盖新观察。
- 共享景点不继承其他行程的“必去”标记，当前行程的必去锚点仍单独注入。
- 天气缓存按地区、数据源和UTC采集/过期时间存储真实预报日期；到期或中国日期跨天后刷新，不平移、不编造超预报窗口的天气。
- 完整行程缓存最长复用1小时；新契约版本隔离旧缓存，过期行程仍保留在库中。命中后仍按本次日期核验天气和导入价格，并重新检查餐饮人均及榜单证据；失效人均回到未知，过期榜单标签移除，不改变已有路线的地点和坐标。
- 同地区的并发天气刷新合并；不同地区可并行。刷新失败有界冷却，保留错误码和Retry-After，不把过期预报伪装成最新数据。数据库不可用时仍可使用真实线上结果，避免写入失败后重复调用。
- 热门城市分批预热；最近30天访问过的有效城市加入更新队列。配置城市持续保留。每轮城市数受限，任务状态和执行租约持久化，后台和手动执行避免重复更新同类任务。
- 上游调用健康率与本地命中分开统计，防止大量缓存命中掩盖上游故障。检索决策、补查原因、来源、价格有效性保留在追踪记录中。

## 配置

见 `backend/.env.example` 的本地资料库与天气缓存部分。默认本地优先开启，预热北京、杭州、上海、成都、西安；地点观察7天失效、每24小时计划采集一次；天气默认1小时且不跨中国自然日。具体频率应按配额、访问量和上游更新规律调整。

后台通过FastAPI lifespan启动；必须以单worker运行。未配置本地高德Key时不启动隐式联网任务。现有MCP传输沿用统一地图边界，后台请求也遵守全局上游限速。

从backend目录手动执行（PowerShell示例）：

```powershell
.\.venv\Scripts\python.exe scripts/warm_catalog.py --cities 杭州 北京
.\.venv\Scripts\python.exe scripts/warm_catalog.py --cities 苏州 --kinds attraction restaurant
.\.venv\Scripts\python.exe scripts/warm_catalog.py --status
```

`--force`忽略计划更新时间，但不绕过正在执行的任务、天气失败冷却或上游限流。`--db`可指定独立采集库，不影响当前行程数据库。正常返回零候选被记录为采集失败，不删除原观察、不续期。

## 检索和数据边界

当前采用结构化过滤与来源事实的词项检索，为模型提供候选上下文；没有调用embedding服务或建立向量数据库。价格、日期和排除项由代码检查，模型仍可通过新的受限工具查询补充语义偏好。

仅采集公开榜单或配置的地图服务真实返回的信息。门票、酒店价格证据仍由现有`import_prices.py`显式导入；餐厅人均属于参考估计。不得把模型生成的解释、推断标签或房价当成已核实事实。

热门城市的首轮采集也只是有界样本，不代表全城完整数据，更不代表已覆盖全国。扩大覆盖应增加城市和合法数据来源，通过冷/热请求的上游调用数、P95耗时、已核验案例的约束满足率验证效果，不能凭返回数量声称召回率。

## 当前部署限制

SQLite、进程内并发合并与单后台工作线程面向当前单进程应用；多副本部署需要共享任务租约、限流和并发协调。后台采集不能替代出行日期对应的实时房态、动态房价和交通核验。测试用隔离数据库和替换外部I/O验证行为，不能替代线上规模与质量评测。
