# 项目复查与执行建议（2026-10-19）

本次检查以当前工作目录源码和本地保存结果为依据，覆盖 Python 编排、工具/MCP、会话及局部编辑、数据检索与价格、监控、Vue 行程展示、Java 社区和 CI/部署配置。门票链路直接修复，其余项目列为执行建议。源码中已有大量未提交改动，本次不会将整个工作区重置或提交。

## 门票为什么一直没有真实价格

最近检查的三份杭州行程，景点大多得到 `static_estimate=100`，即预算预留；这不是景点报价。前端已经能显示数值，主要问题在证据获取与数据覆盖：

1. 内部 `price_observation` 表仅有 1 条记录，无法支撑多数景点；固定官网解析只有故宫、成都熊猫基地两组。
2. 地图名称如“杭州西湖风景名胜区-曲院风荷”，网页常写“曲院风荷”。原来要求完整字符串一致，实际日志大量出现 `VENUE_OR_CITY_MISMATCH`。
3. 通用解析依赖很窄的成人票正则，漏掉“门票价格”“全价票”“免费参观”、表格分列以及成人/儿童价格写在同一句的情况。
4. 顺序查询共享 10 秒，前一两个景点耗尽预算，后续出现 `WEB_QUERY_BUDGET`。配置有次数上限并不等于每个景点都获得了查询机会。
5. 搜索结果可能与景点无关；有官网只返回 JavaScript 应用框架；部分政府页面返回 403/412。公开网页存在，不等于当前纯 HTML 抓取器一定能取得价格。
6. 原价格表主键不包含适用日期。同一 POI、同一来源查不同日期，后写入会覆盖先写入，导致其他日期再次未命中。

## 本次直接修改

- `ticket_policy.py`：解析景区层级名称的子景点别名；保留城市约束，不能把父景区、其他景点或儿童优惠票套给目标景点。支持普通入场票价、免费参观、表格分列和有明确起止日期的淡旺季规则。
- `ticket_web.py`：搜索结果按景点名称筛选；处理直接政府链接、跳转链接，单个跳转失败继续尝试其他结果；说明动态页面/访问验证；新解析版本与旧失败缓存隔离。
- `ticket_pricing.py`：先内部证据、再固定官网、再网上补查；普通网页补查开关与固定官网开关解耦。最多 3 路查询并行，按批次分配剩余时间，默认最多 12 个唯一地点/日期查询，沿用总时间预算与共享限流。网页缓存读取不受剩余网络时间阻止。
- `price_catalog.py`：价格观察主键加入适用日期范围，首次写入时事务迁移旧表，保留原有价格证据。
- Vue 页面及导出：统一门票文案；预留项显示“票价待核实 · 预算预留 ¥100”，计入待核实项；预算卡提供原因与原始来源，导出也保留参考政策/预留的区别。

可靠免费证据仍显示 0 元；未知不当免费；预留金额仍计入参考预算。没有得到可靠网页证据时，不填充猜测价格。纯 HTML 解析尚不支持任意 JavaScript 购票页面，也不支持把价格区间或无法确定票种的小数金额强行转换成唯一整数报价。

## 非门票部分：建议按此顺序执行

### 1. 优先修编排成功率与失败后的修复入口

**发现：** `backend/app/agents/graph.py:76` 的编排、身份/餐次复核和路线舒适度检查共享两次尝试。餐饮选择两次没通过后，路线检查即使发现一天超过 660 分钟，也没有剩余重排机会。真实保存结果已出现餐厅超过 4 公里、可替代时重复选店、单日 782/803/966 分钟等问题。继续增加提示词并不能证明这些组合可行。

**建议：** 在模型选择之前，按住宿候选、游览片区和餐次计算兼容候选与粗略时间余量；让统一编排 Agent 在这些可行组合中选择。错误采用结构化的 `module/date/constraint/current/alternatives`，汇总身份、距离、时长、预算问题后做有界修正。使用整个任务的调用次数、耗时和 token 上限，不把每个错误各自无限重试。

**验收：** 同一组固定候选、天气、路程数据下，输出仍满足景点/餐饮/酒店候选池约束；规定总调用预算；同时统计完整交付率、失败原因分布、token 与 p95 耗时。失败时保留明确原因。

**相关缺口：** `backend/app/api/routes/dialog.py:86` 拒绝把不完整结果导入会话；`frontend/src/views/ChatView.vue:237` 只允许成功行程显示编辑器。因此用户拿到部分结果仍不能直接修正某一餐。

**建议：** 增加“修复草稿”操作，保留稳定模块和候选快照，校验通过才生成新正式版本；原版本不覆盖。不要简单取消所有校验限制。

**验收：** 失败版本修复第二天晚餐，不重采未变更景点；重新算受影响路线和全程预算；请求幂等、版本冲突拒绝、失败保留原版本均有集成测试。

### 2. 建立价格与检索覆盖率的运营闭环

**发现：** 现有目录预热主要采集 POI 与天气，高德 POI 本身不提供可靠门票。预热更多 POI 不会自动形成门票价格库。`candidate_search.py` 的本地命中主要按候选数量衡量；目录检索是 SQLite 词项召回，不能把“有结果”解释成“实际需求被覆盖”。

**建议：** 针对热门城市维护官方参观须知/票价页的来源注册表，按 POI、入场产品、适用日期和更新时间存证；稳定页面用定时采集，动态页面用专用适配器或离线浏览器采集，避免全部塞进用户等待的生成请求。餐饮覆盖按早餐可用性、片区和用户约束评估。先用标注查询集测 Recall@K/可用候选覆盖率，再决定是否添加向量召回与重排。

**验收：** 区分真实价格覆盖率、可靠免费覆盖率、预算预留率、网页失败率和价格证据过期率；预热任务失败不延长旧证据有效期，过期记录重新核验。

### 3. 统一观测与交付边界

**发现：** 主生成的 `_finalize` 已隔离监控写入异常，但 `backend/app/services/partial_edit.py:362` 仍直接调用 `monitoring.record`。监控存储异常可能再次把已经算好的局部修改变成异常响应。普通生成、局部编辑、缓存刷新应共享同一观测失败处理约定。

**建议：** 抽取统一交付记录服务，监控失败提供明确警告和服务日志；业务结果是否通过仍由业务校验决定。报告区分语义查询失败、HTTP 失败、重试、缓存命中和未知日志状态。

**验收：** 向主生成、局部编辑、缓存命中分别注入监控写入故障，验证不丢失业务结果、不改写校验结论、不把未知日志状态算成功。

### 4. Java 社区上线前补齐鉴权和可靠消息

**发现 A：** `java-community/.../controller/LikeController.java:38` 直接信任 `X-User-Id`，客户端换一个值就能换身份；它是演示身份占位，不能作为真实“一人一赞”的身份保证。

**建议：** 与 Python 登录体系统一验证身份，或由网关验证会话后注入服务端可信身份，公开入口剥离客户端自带用户头。

**发现 B：** `java-community/.../service/LikeService.java:92` 先成功更新 Redis，再向内存队列 `offer`。队列满会丢记录但仍返回成功；进程在入队后重启也会丢未落库记录。`:184` 将批次移出队列后，数据库异常再入队也未检查所有 `offer` 结果。

**建议：** 在 Lua 中同步写 Redis Stream 或采用事务 Outbox；消费者持久化后 ACK，失败可重放，数据库唯一键幂等。保留积压、重复处理、失败重试指标。

**验收：** 在 Redis 成功之后/数据库写入之前杀进程，再启动后 MySQL 与 Redis 对账一致；队列满不能静默宣称完全成功；伪造身份不能增加独立用户点赞。

### 5. MCP 和运行时扩容按实际瓶颈优化

**MCP：** `backend/app/services/mcp_adapter.py:44` 每次调用重新建立 transport/session、initialize、list_tools。stdio 模式还会反复启动子进程。建议按服务生命周期复用会话与工具 schema，断线重连时刷新；保留 schema 校验、工具白名单、超时和错误码。先对照测握手耗时与工具执行耗时，不假定 MCP 是当前本地 REST 模式的主要瓶颈。

**任务执行：** `runner.py` 的 `_active_runs` 与会话锁主要保证单进程互斥。单机开发可用；增加多个 worker 前，应改为持久化任务租约、原子版本更新和失效回收，避免多进程重复执行和重复计费。

**验收：** 多个并发恢复请求仅一个获得执行权；服务重启后可恢复；MCP 重连不会取消结果校验或重复执行已经提交的节点。

### 6. 让评测和文档反映当前架构

**发现：** README 仍描述 v0.6 的酒店后选链路、169 个测试及旧版 11 次 LLM 调用数据。这些可以保留为历史实验，但不能当作当前联合编排架构的指标。现有端到端评测案例较少，很多单测通过不等于真实检索命中或模型编排成功率高。

**建议：** 更新架构图和“历史实验/当前实测”标签；建立小型可回放场景集，包含预算很低、固定酒店、免费街区、景区子地点、距离不合理、旧票价、429、动态票务页、部分修改与断点恢复。离线用记录的公开页面/候选/路程验证工程契约，在线用明确授权的合成请求测实际模型与来源质量，二者分开报告。

**CI：** `.github/workflows/ci.yml:64` 只构建前端，未运行已有 `npm test`；Java 没有对应测试作业；后端测试和覆盖率重复跑一遍，可合为一次覆盖率测试。建议先把现有前端测试接入，再增加关键界面及跨服务故障测试。

本次在 Node 22.23.2 下还复现了现有 `node --test tests` 脚本将目录当模块而失败的问题。显式指定 `tests/itinerary.test.mjs tests/planningFlow.test.mjs tests/tickets.test.mjs` 可运行且 12 项通过。建议调整测试发现命令并锁定 CI/本地 Node 版本。生产构建主 JS 包约 1.71 MB（gzip 538 KB）；建议对社区、导出等非首屏功能使用路由懒加载，再测实际首屏时间，避免仅凭包体积推断用户体验。

**验收：** 构造门票金额、来源与预算明细不一致的错误，CI 必须拦截；所有性能/成功率数字标明版本、日期、样本量与统计口径。
