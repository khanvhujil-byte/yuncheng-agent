# 行程生成性能修复

## 实际问题

2026-10-19 00:43 的杭州三日任务实际耗时92.92秒，调用模型17次。首次酒店选择约14.2秒，首次23段串行路线查询约29.5秒；体验复核失败又触发完整编排、选酒店及补路线，增加约27.8秒，最终仍有午餐过晚、单日超长的问题。日志里的旧节点elapsed_ms是“请求开始至节点完成”，不是单节点耗时。

## 修改

- 已有结构化关键词直接通过工具运行时检索景点；美食标签由餐饮采集处理。天气直接读取同一日期对齐和错误重试工具。可显式开启旧ReAct作为对照实验。
- 酒店直接检索、按全部实际景点时长加权排序、用POI ID结构化选址。复核重排复用同日期/城市/需求候选，按新景点重新排序、刷新日期价格。排序考虑总预算，未知房价明确保留固定预算预留；用户硬价格上限需要对应日期证据。
- 所有日期先收集路线OD，精确去重后最多4并发；请求继续经过同一高德Key限流。物理调用总上限48次，包含重试并跨重排累计；单次体验补全含补边共用默认12秒预算，剩余预算传入原HTTP/MCP传输层。同步在途网络请求仍需收尾，极端墙钟可能略超预算。无效Key/配额耗尽的阻断码跨补边与同一运行保留。
- 只将真实路线写入SQLite，默认缓存15分钟，区分方向、精确坐标、交通方式、城市、local/MCP配置。错误与估计不写共享缓存，失败代码和重试记录保留。
- 编排先按建议游玩时长给三餐/交通/休息分配空间；按片区优化可选景点顺序，三餐按时钟选择插入位置。仅普通全量规划可减少可选景点，并明确说明原因；保留必去及原游玩时长。局部修改、美食优先锚点保持原约束。
- 实查路线后允许一次有界的本地修复及补边；复核仍失败时给模型全部错误，不再只反馈第一条。
- 可选社区热度短超时，并缓存成功结果/冷却失败。节点自身计时、重复节点和累计耗时分别记录到监控和SSE事件。

## 验证口径

整套回归在隔离数据库中运行，禁止真实外网。另在本地用原失败任务的景点/餐饮/酒店和首次模型输出回放，以每段25分钟、30毫秒延迟的固定路线适配器检查跨天并发、排程修复及校验。

该回放一次编排模型输出即可通过，三天均630分钟、午餐不晚于14点；模型调用由原实际17次的链路减少为回放1次。回放墙钟不能用于宣称真实生成耗时，网络和模型耗时需另行实测。

真实联网测速未执行：自动审批拒绝了“读取项目密钥并向外部服务发送历史请求”的动作。实现和本地回归不依赖该动作。

## 配置

默认 `ATTRACTION_USE_AGENT=false`、`WEATHER_USE_AGENT=false`、`HOTEL_USE_AGENT=false`，环境里显式配置会覆盖代码默认值。路线参数为 `ROUTE_MAX_WORKERS=4`、`ROUTE_BATCH_BUDGET_SECONDS=12`、`ROUTE_CACHE_TTL_SECONDS=900`；`COMMUNITY_HOT_TIMEOUT=0.35`。

未取得实际报价的门票、住宿、餐饮仍按各自已标明的预算口径展示，不能以提速为由按免费处理。缓存过期、硬交通限制、预算结论与多轮局部修改仍经过原独立复核。
