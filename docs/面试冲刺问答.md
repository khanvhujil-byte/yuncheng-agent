## 一、必须能讲清的主线

### Q1：请用一分钟介绍项目。

**口述答案：**

这是一个旅行规划和行程分享项目。用户填写目的地、日期、天数、偏好、必去景点和预算，系统查询景点与天气，生成逐日计划，再检查必去项、重复安排和估算时间，选择酒店并计算费用。Vue 前端负责表单、进度、地图和行程展示；Python 后端使用 FastAPI 和 LangGraph 组织规划流程；Java 后端使用 Spring Boot、MySQL 和 Redis 实现发布、点赞和排行榜。项目比较关注结果是否有依据，例如区分已知、估算和未知费用，查不到的数据会明确提示。

**记忆顺序：** 用户需求 → 输入输出 → 三块架构 → 一个具体特点。

### Q2：为什么做这个项目？解决了什么问题？

**口述答案：**

旅行规划要把很多分散信息组合起来，还要同时满足日期、必去景点、住宿和预算等要求。模型可以快速整理攻略，但可能漏掉必去项、重复安排景点，或者给出没有依据的价格。这个项目把外部数据查询、模型规划和代码检查连起来，让用户拿到逐日行程，并能看到哪些要求满足了、哪些信息还不确定。

**追问：现在保证真实可执行了吗？**

还不能作这样的保证。线上时间检查使用游览时长和通勤估算，地理跨度使用坐标计算；开放时间、真实道路、预约和实时价格没有形成完整保障。

### Q3：完整请求链路怎么走？

**口述答案：**

先校验日期、城市和必去景点，统一天数、晚数与结束日期。通过后并行查景点和天气，然后把候选数据交给模型生成逐日计划。代码检查结构、必去覆盖、重复项与估算时间，不合格时把原因反馈给模型，进行有上限的重排。接着根据实际行程选酒店、计算费用，再独立复核预算，最后组装结果并决定能否缓存。

**节点顺序：**

`validate_city → [collect_attractions ∥ collect_weather] → compose_plan → verify_plan → resolve_hotel → patch_budget → verify_budget`

结构或行程检查失败可以回到 `compose_plan`；预算超限也有独立的重排计数器。重试耗尽后必须保留未解决的原因。

### Q4：三块系统分别做什么，为什么有 Python 和 Java？

**口述答案：**

Python 负责模型调用、工具查询、规划编排和本地任务记录；Java 负责发布、点赞、排行等社区业务，并持有社区 MySQL 数据；前端负责用户交互与展示。这样能让规划逻辑和社区业务分别演进。代价是多服务部署、接口联调、鉴权和故障处理更复杂。对这个项目的规模，单服务也能实现，双服务有学习和职责拆分的考虑。

**追问：Python 与 Java 互相调用什么？**

Python 可以读取社区热度辅助规划，Java 可以请求 Python 生成行程摘要。用户生成行程后可以选择发布，不会每次生成都自动发布。

### Q5：项目里的 Agent 到底怎么实现？

**口述答案：**

后端给模型提供任务、角色说明和允许调用的工具列表。模型返回工具名和参数，服务端检查权限并执行对应函数，例如调用高德搜索景点。工具把完整实体放进上下文收集箱，把简短结果作为工具消息交回模型；模型根据结果继续选择操作，直到不再调用工具，或者达到步数上限。

**四步记忆：** 模型提出操作 → 服务端执行 → 返回工具结果 → 模型继续决策。

**追问：模型能直接执行 Python 吗？**

这里不能。模型输出结构化的调用请求，由后端解析和执行。工具消息使用 `tool_call_id` 对应到那一次调用。

**追问：项目是完全自主规划吗？**

顶层节点顺序由代码固定，部分节点内部由模型选择工具与步骤。逐日排程使用结构化生成调用，不经过同一套工具循环。

### Q6：为什么拆多个角色？会增加成本吗？

**口述答案：**

景点、天气、酒店和行程编排的输入、工具和失败方式不同，拆开便于限制权限、分别测试和定位问题。景点与天气也可以并行查询。代价是增加模型调用、token 和流程复杂度。天气这类固定操作可以考虑直接调用工具；是否需要 Agent，要看它是否需要选择工具、调整搜索策略，以及收益是否覆盖成本。

**别说：** 多 Agent 一定比单 Agent 更快或质量更好。当前没有充分证据支持这种泛化。

### Q7：怎样减少模型编造？

**口述答案：**

首先用外部接口建立候选池，让模型围绕这些实体排程；然后用代码检查必去项与候选依据。生成后再从候选实体回填 POI 标识、坐标、图片和费用状态，避免直接采用模型随意生成的字段。查不到的天气和价格保留缺失状态，并向用户说明。这些措施降低错误风险，但不能消除所有事实和规划错误。

**追问：POI 是什么？**

地图中的地点实体，例如一个景点或酒店，通常包含地点 ID、名称、地址和坐标。ID 比只比较名字更适合去重和匹配。

### Q8：为什么数据要放进“收集箱”，不全部塞给模型？

**口述答案：**

接口结果通常很长，全部进入消息历史会反复占用 token。工具把完整实体保存到 `ToolContext`，只把数量、结果摘要或必要的候选信息交给模型。后续节点仍能使用原始数据，模型上下文也更短。排程前还会筛选候选，优先保留必去项，再选择评分等因素较好的其他候选。

**追问：压缩会不会漏掉必去景点？**

当前筛选逻辑先保留全部必去锚点，上限还会考虑天数和锚点数量。但其他候选被裁剪仍可能影响选择空间，需要质量评测。

### Q9：你做了哪些校验？

**口述答案：**

可以分四层。输入预检检查日期、城市和必去容量；结构与业务检查使用 Pydantic 和代码检查 JSON、字段、天数、日期、必去项及候选依据；独立行程复核检查重复景点、游览加通勤估算和地理跨度；预算复核在费用汇总后比较上限，并区分费用是否已知。严重错误用于反馈重排，提醒类信息展示给用户。

**追问：独立复核也是让另一个模型评分吗？**

当前 `verify_plan` 和 `verify_budget` 主要是代码规则。它们的判断更容易重复运行和写测试，但判断能力受规则与输入数据限制。

### Q10：为什么要设计费用三态？

**口述答案：**

已知免费、估算价格、查不到价格代表不同的信息。如果都用零元，系统会低估成本。项目把费用分成 `known`、`estimated`、`unknown`；未知金额使用 `null`，单独列入未知项。已知与估算相加得到当前小计，存在未知项时不能把小计解释成完整旅行总成本。

**例子：** 上限 2500 元，已知与估算小计 1800 元，但门票未知，应该提示“预算无法确认”。如果已知免费，才可以记录为已知的 0 元。

### Q11：预算结论有哪几种？success=true 就代表预算满足吗？

**口述答案：**

没有上限时不做预算约束；已知费用已超上限，结论是 `known_exceeded`；加入估算后超限是 `estimated_exceeded`；还有影响判断的未知项时是 `unverified`；没有未知项且小计未超限是 `within`。`within` 也只在当前数据和估算口径下成立。

`success` 还涉及有没有行程、是否降级以及有没有未解决的校验问题。当前 `unverified` 本身不会单独让整份结果失败，但会提示用户；有预算要求时，这类结果不能进入正常缓存。因此要同时看交付状态和预算状态。

### Q12：为什么先排景点再选酒店？酒店怎样选？

**口述答案：**

住宿位置应该参考实际会去的景点。候选池里有些地点最终不会安排，过早选酒店会把这些地点也算进去。排程后，工具对候选酒店计算到实际景点的加权平均距离，权重使用建议游览时长，形成排序；Agent 可以调用驾车距离工具进一步核查，然后通过 `choose_hotel` 保存选择。

**追问：距离怎么计算？**

初步排序使用坐标的 haversine 直线距离；另有高德驾车距离工具可供核查。不能把初步排序分数当作真实路网最短通勤时间。

**公式理解：** 对每家酒店，将“到每个景点的距离 × 该景点权重”相加，再除以总权重，优先考虑结果较小的酒店。

### Q13：遇到过什么具体问题？怎样排查？

**项目记录中的案例：住宿费意外为零。**

现象是酒店有每晚价格，但住宿合计为 0。这类错误不会一定引发接口异常，却会让用户低估预算。用每晚 260 元、住 2 晚建立预期，应该算出 520 元。排查时沿着酒店价格、预算节点读取的晚数和状态写入位置逐层核对。项目记录的根因是曾使用未在 `TripState` 中声明的晚数字段，后续节点没有得到预期的值，缺省为 0。当前预算统一使用状态里的 `nights`，并有住宿按晚数计算的测试。

**表达要求：** 没有亲自复现过，就说“项目记录里有这个问题，我梳理了它的原因”。不要说成“我在线上发现并解决”。

**可以带走的方法：** 先用明确输入算出预期，再逐节点核对字段和值，最后补业务断言。接口返回 200 不能证明金额正确。

### Q14：还有什么适合讲的流程问题？

**案例一：检查顺序错误。**

旧流程在 `verify_plan` 检查单日费用占比，但当时酒店还没选、预算还没汇总，检查无法按预期触发。现在在 `patch_budget` 后增加 `verify_budget`，在数据产生后再检查。单日费用超过 60% 是提示，不等于违反总预算。

**案例二：预检失败，下游仍然执行。**

旧图景点分支使用条件边，天气分支却使用普通边。预检失败时，普通边仍然触发下游。当前两个分支都受预检条件控制。理解这个问题要检查所有出边，不能只看某一个路由返回了 END。

**选一个讲完整即可。** 讲清现象、影响、证据、原因、修改与验证，比堆三个问题更有用。

### Q15：错误以后为什么还要重试？怎么避免死循环？

**口述答案：**

模型可能修正漏掉的景点或不合适的安排，所以把具体错误加入下一轮输入，比重复原请求更有针对性。执行必须受步数和重排次数限制，耗尽后输出未解决的原因。结构与行程检查使用原来的重试计数，预算重排单独使用 `budget_retries`，避免成功排程没有增加原计数、预算持续超限而反复循环。

**细节：** `BUDGET_RETRY_LIMIT` 当前为 2，但实际回边次数要结合“节点先更新计数、条件边再判断”的代码理解，别只根据常量说“额外重排两次”。

### Q16：生成要很久，前端怎样看到进度？为什么用 SSE？

**口述答案：**

前端提交后台任务，后端先返回 `thread_id`。后台执行图，每完成一个节点就记录进度事件；前端通过 SSE 接收进度和最终结果，连接有问题时可以按任务 ID 查询结果。这里主要需要服务端单向推送，SSE 的通信形式比较贴合需求。

**追问：这是模型逐字流式输出吗？**

主要是节点级进度，例如景点收集完成、开始选择酒店，不等于逐 token 输出。

**追问：为什么同步图调用的接口用 def？**

当前图和相关调用是同步的，直接放进 `async def` 会阻塞事件循环。当前同步接口交给线程池执行；要改为真正的异步，需要连同底层调用一起改。

### Q17：状态持久化和断点续跑做到什么程度？

**口述答案：**

任务事件、状态、结果和节点 journal 会保存到 SQLite，查询时可以从数据库重建记录，也有手动重建状态并选择入口继续执行的能力。但是后台执行仍依赖本进程守护线程，进程重启会中断正在运行的工作，保存了状态不等于会自动继续执行。当前恢复覆盖和多实例任务协调仍然有限。

**追问：下一步怎么做可靠？**

先补齐恢复点与新增节点的衔接，再使用持久任务队列、工作进程、超时和心跳，处理任务重复执行与幂等。当前不能声称已有完整可靠的分布式工作流运行时。

### Q18：缓存怎么设计？有什么风险？

**口述答案：**

系统对请求的关键需求生成稳定指纹，用 SHA-256 作为查询依据，缓存满足准入条件的行程。预算上限也参与指纹，避免不同预算混用结果。降级、未解决约束和有预算但无法确认的结果不能当作正常答案缓存。

**追问：当前最大风险是什么？**

当前会按需求形状跨日期复用，再更新日期相关信息；真实旅行里开放时间、预约、天气和价格都可能随日期变化。还需要完善有效期、版本和日期相关复核，不能认为相同偏好的不同日期完全等价。

## 二、Java 后端岗高频追问

### Q19：点赞为什么用 Redis 和 Lua？

**口述答案：**

点赞需要检查频率、一人一赞、更新计数和排行榜。Lua 把这些操作放在一次 Redis 脚本执行中，避免其他请求插入中间步骤。具体先更新限频计数，再用用户集合的 `SADD` 返回值判断是否首次点赞；只有首次点赞才增加计数并更新 ZSET。

**关键纠正：** 单条 `SADD` 自身已有原子语义，不会让两个相同成员都返回新增成功；脚本的价值是把去重结果与后续计数、排行等操作一起执行。

**追问：Lua 出错会自动回滚吗？**

不能作这样的保证。脚本执行的原子性不等于数据库式回滚；也不能把 Redis 与 MySQL 的写入理解成同一个事务。

### Q20：Set、String、ZSET 分别存什么？限频怎么做？

**口述答案：**

Set 保存某个行程的点赞用户，String 保存计数，ZSET 保存行程 ID 与点赞数分值。限频使用用户维度计数，第一次增加时设置 60 秒过期，当前阈值为每分钟 10 次。这是首次请求启动过期窗口的计数方式，不是精确滑动窗口，窗口边界仍可能出现突发。

**细节：** 限频在去重前执行，重复点赞请求也会消耗限频额度。达到限频不代表 Redis 完全没有写入，因为限频计数已经发生。

### Q21：点赞为什么异步落库？如何避免重复写？

**口述答案：**

Redis 操作成功后，Java 把点赞流水放进进程内有界队列，后台每秒最多取 500 条写 MySQL，减少逐次写库开销。数据库通过行程与用户的联合唯一键，以及 `INSERT IGNORE` 避免重复流水；然后从流水重算计数，重复处理时不因直接加一而重复计数。

**边界：** 这种去重解决的是重复处理问题，不能解决事件从来没有到达数据库的问题。

### Q22：能保证点赞不丢吗？Redis 和 MySQL 强一致吗？

**口述答案：**

当前 Redis 先更新、MySQL 后写入，中间允许暂时不一致。实际落库使用 Java 内存队列，进程异常退出或队列满时仍可能丢事件。Lua 虽然也写了 `like:pending` 列表，但还不能据此宣称已有可靠恢复消费者。要增强可靠性，需要接通持久消费、确认、重试与对账，并继续用数据库唯一键保证重放幂等。

**不要说：** 已经实现 Redis Streams 消费组、至少一次投递、强一致或生产级零丢失；当前代码不支持这些结论。

### Q23：怎么防缓存穿透？鉴权做了吗？

**口述答案：**

查询行程存在性时先查 Redis，缺失后再查 MySQL；如果数据库确认不存在，就写短时间空标记，避免相同无效 ID 反复访问数据库。当前空标记有效期是两分钟。

Java 用户身份目前仍使用 `X-User-Id` 占位，可以伪造，不能称为正式身份鉴权。Python 侧有 API Key 等接口保护，但没有统一的 JWT 身份体系。后续应在可信身份基础上做权限和限频。

## 三、效果、优化与 Agent 岗追问

### Q24：项目最后取得什么效果？有没有数据？

**口述答案：**

功能上打通了需求输入、数据查询、行程生成、规则验证、预算提示和社区分享。性能方面，仓库保存了一组上下文压缩对照，每组 3 次运行，token 中位数从 21755 降到 13549，约下降 38%。这个结果只能说明小样本中的改善，不能直接推导所有场景都提升或质量完全不变。

如果被问 Java 压测，可以补充：历史单机测试为 500 个用户、并发度 128，记录约 QPS 456、p99 334ms。这是短时测试，不是长期稳定承载能力。

**如果不熟悉原始记录：** 先讲功能效果，数字放到对方追问时再讲，不要把没跑过的实验说成亲自做的。

### Q25：为什么一次生成这么慢？怎样优化？

**口述答案：**

要先看节点耗时、模型调用数、token 和工具调用记录。历史实验里酒店选择是比较明显的耗时部分，不能只凭感觉优化所有节点。可以限制搜索和工具循环次数，压缩候选上下文，对独立查询并行执行，并把固定步骤改为直接调用工具。每次优化还要复核必去覆盖、未知信息和规划规模，避免速度更快但结果变差。

**追问：并行一定减少一半时间吗？**

不会。并行阶段主要取决于较慢分支，还受共享资源与外部请求影响；整个请求还包含后续串行步骤。

### Q26：测试和评测有什么区别？

**口述答案：**

单元测试检查确定性行为，例如三天两晚的住宿费用、未知项不能被判为预算满足、无效输入不能进入下游。外部接口应 mock，数据库隔离到临时目录。评测用任务集检查规划结果和代价，包括必去覆盖、重复、时间估算、预算状态、降级、耗时与 token；最好有明确规则和原始记录，不能只让模型说自己做得好。

**追问：只看接口成功率够吗？**

不够。请求返回正常可能仍漏景点或算错费用；代码单测通过也不代表真实用户旅行满意。

### Q27：CP-SAT 是什么？当前项目用到哪里？

**口述答案：**

CP-SAT 是一种约束求解方法，可以把景点是否安排、安排在哪天和开始时间转成变量，再加入必去、时间窗、游览时长及通勤等约束。当前项目有独立的离线 spike，输入固定候选和结构化约束，对比固定排期基线与 CP-SAT；它还没有替代线上模型排程，也没有评测自然语言约束抽取。

**结果口径：** 当前任务文件与结果覆盖 11 个任务、两组方法、每组每任务重复 3 次，共 66 条结果。现有摘要部分文字仍写 10 个，以任务与结果为准。

### Q28：找到可行排程就代表预算和现实旅行都可行吗？

**口述答案：**

不能。求解结论只对应编码进模型的约束与数据。当前通勤主要使用直线距离折算，费用还有估算和未知项；现有结果中也有排程 FEASIBLE、预算却为 `estimated_exceeded` 或 `unverified` 的案例。需要分别展示排程状态和预算状态。求解器证明不可行与搜索结束前没有找到解也要区分，不能把 UNKNOWN 直接当无解。

**别说：** 已经完成“LLM 排程 vs LLM 抽取加 CP-SAT”的正式在线对照；当前基线不调用 LLM。

## 五、容易继续深挖的实现

### Q33：并行节点怎么安全更新状态？

**口述答案：**

景点和天气节点会同时产生警告、来源和用量信息，所以 `TripState` 对共享字段定义 reducer。列表类记录追加，来源字典合并，token 计数按字段累加。合并规则要符合业务语义，不能把“累加用量”写成“后值覆盖前值”。

**进一步边界：** reducer 处理图节点更新；Agent 内线程并发访问 `ToolContext` 是另一层共享状态问题。不能据此宣称全部共享对象天然线程安全。

### Q34：外部接口失败如何处理？

**口述答案：**

先区分输入错误、外部接口错误和可降级的缺失数据。城市解析失败或明确的上游配置错误应在预检阶段给出明确错误；部分查询失败可以保留已有数据，同时记录来源、警告和错误。模型循环也有异常处理与步数上限。最终结果由统一出口判断完整性，不能把所有异常都吞掉后当作成功。
