## 1. 问题与背景

用户希望 Agent 能理解旅行的整体意图，而不是机械地把景点塞进固定模板。例如：四天旅行中有两天去周边雪山，Agent 应判断是否需要在雪山附近住一晚，避免两天都从市区远距离往返；市内活动集中、通勤合理时，则应优先连住，减少搬运行李。

目前项目已有景点、餐饮、酒店的联合编排，以及真实路线、舒适度和预算校验，但仍以“整程一家酒店”为核心假设：

- `TripPlan.hotel` 和状态中的 `hotel` 表达单家酒店；`hotel_segments` 只是预留字段，缺少入住日期等完整语义。
- 地图默认每天从同一家酒店出发，住宿局部修改只能替换全程酒店。
- 路线、预算、恢复状态和前端不能完整表达“今天从市区酒店出发，晚上住山区，明天从山区酒店出发”。

现有评测报告中的成都四天、两天周边雪山公共交通场景未通过路线舒适度验收。单酒店假设是原因之一；区域交通数据覆盖不足也是独立问题。分段住宿不能保证所有远途要求都能满足，不能通过放松校验或伪造车程把失败变成成功。

**本次产品变化：从“选一家酒店并排景点”升级为“联合安排活动、跨日移动和住宿”。** 这项能力应适用于山地、海岛、古镇、郊区、多片区等场景，不写死某座雪山或某个城市的例外。

## 2. 产品目标与成功标准

### 2.1 目标

1. 理解用户的目的地、主题天数、交通方式、住宿偏好和不可变条件，并在完整行程中兑现。
2. 在真实候选和可核算路线基础上，合理选择连住、分段住或说明不可行。
3. 将省下的通勤与换酒店增加的费用、时间、行李负担一起比较，避免为了“智能”频繁换酒店。
4. 每晚住宿、每天起终点、路线和预算一致，支持单晚及住宿段的局部修改。
5. 对缺失数据、估价、冲突和失败作清晰说明，保留诊断证据。

### 2.2 发布门槛

| 编号 | 标准 | 验收口径 |
|---|---|---|
| S01 | 住宿日期完整且唯一 | 所有标记成功的结果中，应住宿日期恰好覆盖一次，无漏住、重叠、负晚数 |
| S02 | 跨日路线连续 | 每日起终点与前一晚、当晚住宿一致；换酒店交通与必要寄取行李路径无漏算 |
| S03 | 硬约束无静默破坏 | 固定住宿、必去点、主题天数、交通限制和预算上限不被擅自改变；冲突明确返回 |
| S04 | 金额可对账 | 分晚房费、门票、餐饮及已支持交通费用由代码汇总；明细和总额一致，未知费用不按零元处理 |
| S05 | 能换也能不换 | 固定验收集同时包含需要换住、应该连住、换住仍不可行三类案例；逐条满足预先定义的期望 |
| S06 | 修改不覆盖无关内容 | 单晚修改的影响范围正确，其他已锁定内容不变；失败保留原版本，旧版本不能覆盖新版本 |
| S07 | 有界执行 | 每次运行均受现有总时限、模型调用、工具请求、补采和重排上限约束，含重试的用量统计完整 |
| S08 | 可复现与可观测 | 日志能关联候选、方案、路线证据、失败原因、版本、耗时和费用，不输出模型内部思维链 |

上述是验收要求，不是当前完成情况。确定性契约测试全部通过；至少 30 个规划场景逐条验收，不能仅用总体通过率掩盖必测失败。真实接口跑批与离线故障注入分别出报告，不混算。

## 3. 范围与非目标

### 3.1 本期 P0

- 现有国内旅行规划中的多晚住宿安排，包括市内连住、周边过夜、多片区分段和无住宿。
- 景点、餐饮、酒店、跨日移动共同编排；以已核验 POI 为选择范围。
- 当实际活动区域超出出发城市时，按真实地理区域补充酒店、餐饮、天气和路线信息。
- 分晚费用、每日起终点、独立约束校验、局部修改、前端展示及历史数据兼容。
- 对现有交通工具能够提供证据的路线进行规划；无法核验的班次、末班车和山区接驳明确列为待核实条件。

### 3.2 后续 P1

- 有授权的铁路、长途客运、景区接驳和酒店库存数据接入。
- 全国区域住宿与交通数据的持续运营、评价反馈与排序优化。
- 更复杂的跨城环线、夜间交通过夜、多交通接续保障。

### 3.3 本期不做

- 真实订房、支付、取消订单和库存承诺。
- 用模型补造酒店、道路、班次、山区预报或景区营业状态。
- 全国无边界爬取、新建推荐算法训练平台或推翻现有登录、社区等无关模块。
- 将普通行程规划包装为高海拔安全保证。已知封闭、禁入条件必须遵守；信息不全明确提示。

## 4. 用户场景与日期语义

### 4.1 典型场景

| 场景 | 期望行为 |
|---|---|
| 三天市内游，活动区域集中 | 优先连住，不因每天景点略有变化而换酒店 |
| 两天连续在同一远郊区域活动 | 比较市区往返与当地过夜，后者可行且收益明显时分段住宿 |
| 只有一天远郊游，次日清早从市区离开 | 同时考虑回城需求，不能仅因景点远就住远郊 |
| 远郊两天但用户禁止换酒店 | 保持约束；往返不可行时说明冲突并提供用户可选择的调整 |
| 用户已订某晚酒店，其余晚未订 | 锁定该晚，其他日期可以优化 |
| 老人、儿童、大件行李或慢游 | 增加休息、转移和寄存成本，降低频繁换住倾向 |
| 山区酒店无真实候选或交通不可达 | 有限补采；仍无依据时说明缺失，不编造酒店或默认能到达 |

### 4.2 夜晚必须绑定入住日期

“第 2 天换酒店”默认指第 2 天晚上入住的新酒店，不表示第 2 天早晨已经在那里。

例如三天两晚：

| 日期 | 当日出发 | 当日活动 | 当晚住宿/终点 |
|---|---|---|---|
| D1 | 用户提供的到达点；未提供则标记规划边界 | 市内 | A 市区酒店，D1 入住 |
| D2 | A 市区酒店 | 前往山区并游览 | B 山区酒店，D2 入住 |
| D3 | B 山区酒店 | 山区活动及返程 | 用户提供的返程点；未提供则标记末站边界 |

如果 D2 很早就需要在山区活动，Agent 也应评估 D1 晚直接住山区，而不是机械固定“第二晚才换”。选择取决于到达时间、交通、预算和用户要求。

默认 N 天住 N−1 晚，沿用现有显式晚数支持。若住 N 晚，最后一晚退房发生在旅行结束次日；不自动增加一个游玩日。历史显式晚数少于 N−1 时，不擅自补房：缺少哪些夜晚的住宿安排必须澄清或显示尚不完整，不能伪称住宿连续。零晚是明确无需住宿，不能自行添加酒店。

首日到达、末日离开不默认从酒店出发或回酒店。缺少用户实际起终点时，明确路线覆盖范围，不能把未计算的机场、车站交通当作已计入。

## 5. 详细功能需求

### FR01：意图和住宿约束

- 提取活动区域、主题所需天数、具体日期、到离时间、交通方式、总预算和每晚房价上限。
- 住宿策略包括自动评估、尽量连住、必须连住。默认自动评估，同时计入换住负担。
- 区分“喜欢这家酒店”与“已订/必须住这家酒店”；后者是硬约束。
- 支持按入住日期锁定酒店。旧 `fixed_hotel` 维持原有整程固定语义，不在升级时放松。
- “少折腾”“带老人”“行李多”等偏好应进入换住评估；不能自行推断用户已经预订。
- 无法确定锁定日期、酒店分店或互相冲突的硬约束时，提出具体澄清；普通偏好使用可解释默认值。

### FR02：按活动区域召回事实候选

- 先复用内部数据库中与目的区域、有效期、需求匹配的数据，数量、质量或覆盖不足再实时补采。
- 酒店和餐饮围绕实际活动区域、交通节点搜索，不能只查出发城市，也不能把“同省”当作附近。
- 保留 POI 身份、坐标、来源、采集时间、价格状态及适用日期；重名分店必须消歧。
- 酒店评分、设施和价格缺失时按缺失处理，不用通用模板补成高评分、免费停车等事实。
- 候选按片区分组并控制上下文规模；固定酒店、硬性必去点及关键区域候选不得因压缩丢失。
- 补采有次数、请求和总时限限制，429 限速并尊重可解析的重试等待信息，不无限并发。

### FR03：联合编排和方案比较

- 联合编排 Agent 同时选择每天景点、餐饮、每晚酒店及区域访问顺序，输出候选 ID 与结构化计划。
- 候选不足时提出缺失区域与数据类型的补采请求，经运行时校验后有限执行；不能自行发明事实。
- 当出现连续远郊活动或严重折返时，比较连住与分段住宿。没有真实必要的市内行程可直接采用连住，避免为比较增加无效模型调用。
- 先满足硬约束，再比较总通勤、单日负担、换住成本、整体支出和偏好；不采用“距离超过某个固定值就必换”的唯一规则。
- 换住成本至少包含退房、行李整理、寄取行李、抵达与入住时间，以及已知的额外交通/服务费用。没有商家寄存证据时不能默认支持寄存。
- 若两个方案差异不足以支持换住，默认少搬动。权重和阈值可配置，结合评测调节，不宣称一个通用分值适用于所有旅行者。
- 自动调整不得解锁已订酒店、删掉必去点、把“两天雪山”改成市区两天，或放宽预算和舒适上限。
- 原始方案和有限修复均失败时返回冲突及具体可选调整，不消耗无上限 token 继续尝试。

### FR04：路线、营业与舒适度

- 每天从前一晚住处或用户实际起点出发，到当晚住处或真实离开点结束。
- 换住日可直接从旧酒店经活动去新酒店，不要求空跑一次酒店；但行李无法随行时必须安排可核实的处理路径。
- 交通工具计算路线、时间和距离；Agent 选择方案，不能修改事实数值。直线距离不能冒充实际车程。
- 总时长包含景点游玩、餐饮、交通、休息、换住及必要缓冲；避免分别核算导致重复或遗漏。
- 根据实际交通方式检查可达性。公共交通无路线、末班车未知或单程极长时，不自动切换自驾来通过校验。
- 有来源的入住/退房、营业、预约及接驳窗口是约束；缺失时注明假设，并区分“可计算的建议”与“已核实可执行”。
- 大幅不合理的供应商路线结果需标记并有限核验，不能直接据此认定真实车程，也不能删掉结果掩盖问题。

### FR05：按区域处理天气和体验

- 天气绑定访问日期和实际区域；市区天气不能充当山区天气。
- 超出预报窗口、山区覆盖不足或查询失败，显示明确原因及待核实提示。
- 对有证据的封闭、危险天气和不适宜条件调整活动或返回冲突，不生成未经核验的“正常开放”。
- 将海拔、连续长途、游玩强度、休息和同行者偏好纳入安排；无法确认的信息作为风险，不能输出医学或安全保证。

### FR06：完整预算和价格表达

- 住宿按入住日期、酒店、房间数和单晚金额计算，可合并连续同酒店的展示，但不能用一个均价覆盖所有夜晚的事实。
- 延续现有票价顺序：有效内部信息 → 官网/可信网页查询 → 明确标注的日常模型估价；无依据或估价失败保留具体原因，不伪造官方价格。
- 普通商场入场、独立收费展馆、景区入场、索道/接驳等不同项目分开，避免重复计费或统一预留门票。
- 总预算覆盖门票、餐饮、全部住宿晚数和支持计算的交通；停车、过路、寄存等有证据则计入，无证据则注明估算或未包含。
- 沿用现有单人餐饮门票、单间住宿计价，并在 UI 显示口径；如未来加入人数和房间数，先更新对应 PRD，不能默认为家庭总价。
- 明细区分已知、参考估价、预算预留和未知。存在影响总额的未知费用时，不声明最终费用确定在预算内。
- 预算不足时可评估换价位、调整可变活动或降低折返成本；不得暗改硬约束。用户选择调整后才采用相应条件。

### FR07：按晚/住宿段局部修改

- 支持换某一晚、某一连续住宿段或全部未锁定住宿，入口明确日期范围。
- 默认保留其他景点、餐饮和住宿；仅为通过关联校验而需要修改其他内容时，列出连带变化，由用户明确采用扩展调整。
- 修改 D2 晚酒店至少影响 D2 晚终点和 D3 早起点；如寄取行李影响 D2 上午，也须重算相应路线。住宿段修改按真实依赖扩展，而非固定只改当天。
- 重新核算关联路线、舒适度、区域天气需要与整程预算；不重新调用无关的有效数据采集。
- 复用当前版本号、操作幂等键和断点恢复机制。同一操作完成后重试返回同一结果；旧版本请求冲突时不覆盖新版本。
- 运行中操作按已有检查点恢复或返回执行中状态，不重复启动收费链路；恢复时确认租约与状态归属。
- 修改失败保留原计划和具体错误，候选新版本不能作为成功结果写回。

### FR08：前端展示

- 继续将住宿、天气、预算置于行程最前面。住宿显示日期段、酒店、晚数、参考房费、锁定状态，避免长列表挤满页面。
- 换住日显示“从 A 出发，今晚入住 B”和简短原因；连住说明只在有必要时展示。
- 每天行程前放当日地图，分别表达出发住宿、入住住宿和无住宿起终点，不再假设所有日期同一酒店。
- 路程时间融合到景点、餐饮及必要住宿转移卡片中；不恢复独立的冗长时间安排和逐路路程面板。
- 展示“换住收益/代价”的简短事实摘要，例如减少往返时间、增加房费或搬运行李；数值必须取自核算。
- 预算中明确列出景点票价及状态，未知和预留不伪装成票价；天气按相关区域展示，详细依据可折叠查看。
- 用户能在住宿概览直接选择修改范围；手机和桌面均可使用，地图失败不妨碍阅读文字计划。

### FR09：失败和解释

- 区分数据不足、供应商超时、限流、鉴权错误、候选不合法、路线不可达、约束冲突和执行版本冲突。
- 保留结构化 `error_code`、`retryable`、`message`，运行时据此处理，不从中文文案反推错误类型。
- 失败说明包含受影响日期、条件及下一步选择；不能只显示“生成失败”，也不展示内部长候选矩阵。
- 可交付草案必须显著标记未验证项目，与全部约束通过的结果区分；硬约束失败不能标记成功或写入成功缓存。
- 给用户结论和依据，不展示模型内部推理过程。用户拒绝换住时，解释实际代价，尊重选择。

## 6. 拟议数据与系统边界

以下是后续开发的契约要求，不代表现有接口已具备能力，字段名在契约设计阶段统一确定。

| 对象 | 必须表达的信息 |
|---|---|
| 住宿策略 | 自动/尽量连住/必须连住、允许调整范围、偏好及硬约束 |
| 住宿锁 | 酒店身份、入住日期范围、锁定依据；旧整程锁保持兼容 |
| 每晚住宿 | 入住日、退房日、酒店 ID、区域、费用/状态/来源、是否锁定 |
| 连续住宿段 | 同酒店连续若干晚的展示投影，由每晚事实派生，避免双重计价 |
| 当日路线边界 | 日期、实际起终点或住宿引用、交通方式、未覆盖的接驳边界 |
| 方案摘要 | 连住/分段、总路程时间、换住次数与成本、预算、未验证项和采用理由 |
| 校验结果 | 每条约束状态、错误码、日期、证据引用；未知不得等价于通过 |

模型负责意图理解、方案选择和解释；工具负责事实采集、路线与价格查询；代码负责候选绑定、日期、金额、约束校验和运行上限。已有确定性工具不为了增加 Agent 数量改成 LLM 调用。

所有消费单酒店字段的模块都需纳入契约迁移，包括图状态、检查点、提示词、预算、舒适度、局部修改、缓存、持久化、API、前端类型、地图和导出。不能只让模型返回多个酒店，而下游继续用第一家酒店计算。

## 7. 历史兼容、限制与风险

| 限制/风险 | 处理要求 |
|---|---|
| 历史单酒店计划 | 按原日期和晚数只读适配为每晚住宿，保留原来源和价格状态；不自动改写用户数据 |
| 旧执行检查点 | 契约版本隔离；旧任务按旧契约完成或明确提示重新规划，不能中途混用字段 |
| 缓存复用错误 | 缓存键含住宿策略、日期锁、访问区域及契约版本；不复用单酒店旧成功结果冒充新方案 |
| 数据源不覆盖山区交通 | 明确缺失，提供待核实选项；接驳证据不足不能承诺公共交通可行 |
| 酒店价格与库存变化 | 参考价显示采集/估价状态，不保证可订；更换住宿重新按相应日期定价 |
| 退订与行李成本未知 | 固定住宿不自动取消；行李寄存不默认免费或存在 |
| 性能与调用膨胀 | 区域补采并行受限流控制、事实缓存复用、路线去重；预算包含重试与候选比较 |
| 方案比较依赖错误事实 | 来源和异常检测进入日志，避免用精确的错误数字支撑“省时”结论 |
| 需求冲突 | 固定酒店、交通、必去与预算发生冲突时，列出条件和用户可选调整；Agent 无权悄悄放宽 |

运行预算沿用现有配置上限。方案候选数、补采次数和重排次数在实现前登记具体默认值与最大值，并做上限测试；不能靠提高已有舒适度上限解决失败。

性能目标采用同模型、同供应商、同并发条件下的前后对比：记录端到端和分阶段 p50/p95、模型调用、工具请求、token 与重试费用。发布前冻结基线；市内无须分段场景 p95 目标不劣于基线 20%，远郊分段单列统计并受现有总超时约束。该目标待实测验证，不是已取得的指标。

## 10. 默认决策与待核实项

无需反复询问即可采用的默认决策：自动评估、优先减少无价值换住、固定住宿不动、事实不足明确提示、失败不覆盖原计划、现有价格口径不暗改。

长行程允许模型用互不重叠、入住/退房日期明确的住宿段压缩输出，代码先完整展开为每晚事实再校验、计费、保存；对外仍只有一份分晚事实，不引入段级重复计价。真实跑批保留逐场景源代码清单，不将修复前后不同版本拼接成单版本通过率。

真实多区域用例显示餐饮补采3次容易被早期多样性补充占满；默认改为5次（现有配置最大值不变），仍共享原6秒预算。编排前最多1次，剩余供已选布局核对；零可用餐厅/无早餐候选优先于增加多样性。只提高有界召回覆盖，不放宽就近、餐次、舒适或事实校验。

联合编排的有限修复允许同一模型输出最多12项明确餐次ID补丁，运行时合并当前候选方案后仍完整绑定和独立复核。这样修改一个无效餐厅不必重新抄写多天全部ID；不新增模型调用额度，不允许补丁覆盖其他日期、住宿或事实字段。

路线查询在已选方案内优先核验跨区域长途，再核验市内短途，避免共享48次额度先被早期短途及其修复消耗。只改变查询优先级，不改变景点顺序、交通方式、供应商异常判定及未知路线的失败口径；离线验证额度紧张时仍先查询关键长途。
