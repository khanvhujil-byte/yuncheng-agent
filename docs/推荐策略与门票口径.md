## 餐饮推荐

1. 先应用用户排除项和每餐价格上限。未知价格不能证明满足硬上限。
2. 根据酒店和本日景点游玩时长推导餐次位置，先限制附近距离、额外绕行范围。仅用户明确允许全城觅食时解除附近限制。
3. 先按数据源名称/类目匹配餐次：早餐、早茶、豆浆、粥等是偏好信号，不是营业时间证明。仅有明确夜宵、火锅、酒吧等候选且没有早餐信号时，不强行填成早餐。
4. 在上述候选里优先避免同一天重复，再选全程使用次数最少的店。评分、真实榜单、人均、菜系与同品牌分店作为进一步排序依据。未知价格不会按0奖励。
5. 附近只有一家符合条件时允许复用，并显示原因；不为了凑不同餐厅安排跨城绕行。明确已选餐次和局部修改保留原选择。

算法位于`backend/app/services/food_recommendation.py`。它是可解释规则与重排，不是经典MMR的向量版本，也没有新增模型调用。

## 检索充分性与性能

城市范围内“搜到20家”并不意味着当天酒店/景点附近有足够选择。编排完成后再检查餐次与空间覆盖：

- 先查当前城市的新鲜本地POI并应用价格要求，不刷新原数据时间戳。
- 不足时使用高德`place/around`，绑定真实酒店/景点坐标、餐饮类目、4公里半径，按距离召回，并在本地再次过滤越界结果。
- 本地适配和项目MCP服务提供同一`search_restaurants_nearby`契约；旧MCP不支持时返回明确错误，不伪造成功。
- 每次图运行最多3个补充查询，含重排共享6秒预算，单查询最多2次尝试；沿用全局请求节流、429冷却和Retry-After。
- 无效Key、额度或不兼容MCP停止后续补搜。查询身份、耗时与永久错误保存在图状态中，断点恢复继续遵守上限。
- 局部修改不自动补搜或替换其他餐次。补搜记录计入工具监控。

## 门票与消费

后端是唯一预算计算入口，前端展示和导出不能自行给未知票价加100元或改变预算结论。

| 场景 | 行为 |
| --- | --- |
| 有有效日期、票种与来源的门票证据 | 使用来源价格，保留凭据；0元与未知分开。 |
| 明确购物类目下的普通入场 | 不设门票预算，金额0、estimated、venue_policy；说明购物、餐饮及付费项目另计。该分类规则不冒充官网免费票价。 |
| 商场内收费展览、乐园、文化设施，或混合不明确类目 | 不按商场免费推断；收费来源优先。 |
| 酒吧、KTV等消费场所 | 消费/最低消费/可能的入场收费待核实，金额未知；不套用景点统一门票预留，预算不能据此确认满足上限。 |
| 真正待查的景点门票 | 沿用用户选择的固定预算预留，明确不是实际报价，保留具体未核实原因。 |

POI类目从候选数据源回填，模型不能把收费景点改成购物类目以逃避费用。新契约版本为8，旧的完整行程缓存不能直接绕过这些规则。历史版本不会被后台覆盖。

官网适配目前仍只有故宫、成都熊猫基地；没有宣称覆盖全国票价。原因明确区分：尚未接入该地点解析、缺少POI标识、HTTP错误、页面票价缺失/歧义、查询异常及政策日期窗口不适用。应通过新增受控官网适配或已有价格导入接口扩充覆盖，不能用模型记忆填成官方报价。
