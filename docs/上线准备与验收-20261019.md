# 上线准备与验收（2026-10-19）

本次修复基于当前统一编排架构。新增生产部署配置不会自动将本地开发环境变成公网服务。下列工程保障均有明确边界；离线测试通过不等于任意城市的模型规划成功率或官方价格覆盖率达标。

## 1. 门票与预算

流程：内部适用日期的价格证据 → 已维护官网 → 限时网上补查 → 批量模型日常成人门票估算 → 模型不可用时明确预算预留。商业街和普通商场的普通入场按类目规则不设门票预算，付费子场馆另算；消费型场所不伪装成固定门票。

- `llm_estimated` 显示“日常门票参考 ¥金额 · 模型估算”，不生成证据 URL，不存入官方价格观察表；模型估算缓存 7 天。可靠的价格证据优先。
- 每个任务最多一次门票估算批次，默认 15 秒，输出 token 上限 4096。负数、字符串、布尔值、超限金额、未请求地点被拒绝；失败保留可见预算预留。模型或网络不可用时，无法保证提供真实收费金额。
- 预算、景点卡和导出使用同一价格来源契约。0 元的模型估算与有来源的免费政策区分。
- 首次生成、缓存刷新和局部修改均记录新增模型调用和 usage。
- 已成功解析的官方页面进入 `ticket_source` 注册表，后台按日刷新未来 7 天的政策参考；失败不会延长旧证据有效期。维护人员可通过 `backend/scripts/warm_tickets.py --registry reviewed-sources.json` 注册精确 POI 与官方 URL，文件格式为 `[{"city":"城市","poi_id":"高德ID","name":"景点名","url":"已审查的官网HTTPS票价页面"}]`。注册不等于报价成功，查询失败按状态报告。
- 登录后可查询 `/api/observability/tickets`，分别查看数字覆盖、来源价格、模型估算和预留项；不能把数字覆盖解释为官方价格覆盖。

公开合成实测：曲院风荷、城隍阁、杭州博物馆，单次模型调用 3.53 秒，235 输入 token、79 输出 token，返回参考金额 0/30/0 元。三项均为模型估算，不是官方价格核验结果，也不是全国准确率样本。

## 2. 编排与修复

统一 Agent 仍决定景点、三餐和酒店；代码保留城市/候选身份、固定酒店、必去景点、日期、预算、路线和舒适度校验。提示词增加按真实坐标计算的酒店—景点初筛及午餐候选，直线交通预估明确标注为启发式，不冒充实际路程。

结构化候选输出通过后，执行独立复核、实际路线、门票、舒适度、预算，再回喂错误及对应餐次可选 ID。格式/候选身份错误仍限制局部尝试；全任务共享最多 6 次编排调用、180 秒编排阶段和 60000 累计 token 的停止条件，预算超限最多进入 2 轮。已开始的上游调用还有其自身超时，不应将阶段停止条件解读为严格 HTTP 整体 SLA。

失败但具有合法数据结构的行程可以导入会话作为草稿。界面明确标记未通过，可按模块预览；确认后仍重新核验整个方案，失败不替换原正式版本。历史版本、请求幂等键和版本冲突校验保留。

## 3. 运行与观测

- 任务执行使用可续租 SQLite 租约，原子获取，心跳续期；关键日志、结果、快照及会话提交在写事务内校验 token，旧执行者不能覆盖新执行者。正常执行和断点恢复共用路由判断。
- 只支持多个进程共享同一台机器的本地 SQLite。不要将 SQLite 放在 NFS 或认为该机制支持多主机部署。生产模板先运行一个 Python worker；跨主机需迁移持久状态与限流。
- 已提交的节点结果可以恢复；调用上游后、提交日志前发生进程崩溃，仍可能需要重新调用并再次计费。租约不等于跨外部 API 的严格一次执行保证。
- 主生成、缓存返回及局部修改统一隔离观测写入异常，不能把监控故障当成业务校验失败。
- MCP 长驻同一异步任务管理 transport/session，初始化与工具发现复用；请求保留队列上限、截止时间、白名单及 schema 校验。连接异常关闭，下次调用重建；不自动重放已经提交的调用。

## 4. 社区身份和点赞持久化

- Java 不信任 `X-User-Id`。点赞、发布验证 `X-Session-Token`，调用 Python 的登录会话核验端点获取数据库分配的稳定数字身份；过期/撤销会话被拒绝。
- Lua 在一次执行中更新去重、计数、排行榜和 Redis 持久队列。消费者读取而不提前删除，数据库幂等插入和计数重算成功后 ACK；失败、进程重启均可重放。队列达到上限时拒绝新点赞，不能丢弃后返回成功。
- 生产 Redis 开启 AOF、`appendfsync always` 和 `noeviction`，吞吐量必须重新测，旧版匿名身份压测数字不代表此版本性能。
- 老版游客数字身份与新账号并非可验证的同一身份；不要自动把游客历史赞归属到新账号。上线使用新库，迁移旧库时应另行设计历史归属处理。

## 5. 生产启动

1. 运行后端全量 pytest、Ruff、前端 npm test/build、Java mvn verify。CI 已包含三端，不再重复执行两遍后端测试。
2. 配置 `backend/.env` 的模型和地图凭据。复制 `.env.production.example` 为 `.env.production`，填两个不同强密码。密码文件不提交版本库。
3. 执行 `docker compose --env-file .env.production -f docker-compose.production.yml config --quiet`，再执行同一命令前缀加 `up -d --build`。
4. 模板仅绑定 `127.0.0.1:8080`。在服务器网关配置真实域名、HTTPS 证书并反代该端口。MySQL、Redis、Java、Python 均不发布调试端口。
5. 生产模式启用登录会话验证和限流；注册/登录仍开放并受专用限频保护。未登录直接消耗模型的请求被拒绝。Nginx 屏蔽 AI 内部接口、社区内部统计和 metrics 公网访问。
6. 用普通账号完成一次生成、失败草稿修复、局部改酒店、发布和点赞；验证登出后旧会话失效。检查实际 p95、失败分类、门票来源分布、429 与队列积压，再扩大使用量。

`trip_data` 已包含账号、会话、版本、执行日志和价格数据，绝不能再当作可丢缓存。需与 MySQL、Redis 数据卷一起备份；先做恢复演练再对外承诺数据保存。部署更新前备份数据库和代码；回滚代码时须保留迁移后的数据，避免覆盖用户新操作。

## 6. 评测资产与待验证边界

新增回归覆盖模型价格校验与缓存、计费、跨进程互斥、旧执行者隔离、MCP 复用、会话伪造拒绝、点赞 ACK 顺序和重放。既有路线/天气/预算/429/低预算/断点恢复场景继续保留。

`backend/scripts/eval_retrieval.py` 使用数据库快照和人工标注的相关 POI/可用 POI 集，报告 Recall@K 与可用查询覆盖率，不调用模型、不联网。输入格式为 `[{"city":"城市","kind":"attraction","query":"查询","relevant_ids":["相关ID"],"usable_ids":["满足任务的ID"]}]`，运行 `python scripts/eval_retrieval.py labels.json --db snapshot.sqlite --k 10`。标注集必须与城市/日期/数据库快照一致；没有标注时不能宣称检索质量已达到某个百分比。

前端改为路由懒加载，完善测试发现命令。测试数量与本次实际结果见验收记录；README 原 v0.3–v0.6 数字仅保留为历史实验。

## 7. 本次实际验收结果

- 后端全量 885 项测试通过，0 失败、0 错误、0 跳过。随后调整账号限流、失败草稿连续修复和票价刷新日期，相关 55 项专项回归全部通过；全量结果不冒充最后改动后的重复全量运行。
- 前端 13 项测试、TypeScript 检查和生产构建通过。主 JS 包降至约 686 KB（gzip 222 KB），仍有超过 500 KB 的构建提示，后续可继续分包。
- Java `mvn verify` 通过，6 项测试通过并生成可执行 JAR；不等于已完成真实 MySQL 全栈联调。
- 公开地点模型票价探测一次返回 3 个数值，耗时 3.53 秒；这是模型兜底可用性检查，不是价格真实性核验。
- 独立 Redis 实例实际验证首次点赞、幂等去重、强制退出后 AOF 恢复，以及错误计数器不造成部分写入。未修改现有 Redis 数据。
- 生产 Compose 配置语法检查通过。当前 Docker Desktop 引擎不可用，因此没有完成容器整栈启动、真实服务器域名/HTTPS 和公网验收，也没有执行生产环境的社区压测。

上线前仍须在目标服务器完成第 5 节的启动与账号流程验收，并对数据卷做一次可恢复的备份演练。当前测试不能代替真实城市检索标注集、全国票价维护和线上成功率监测。
