# 项目入门与面试陪练

核对日期：2026-10-12。依据当前代码、已保存实验和提交记录整理；本次没有重跑实验或测试。目标是逐步理解项目，能够用自己的话解释实现，随后进行追问练习。

## 学习方法：先理解，再表达，再追问

从用户提供的面试建议中提取六项训练：

1. 项目背景：谁遇到了什么问题，为什么值得做。
2. 项目全貌：输入、输出、主流程，以及本人实际负责的部分。
3. 实现细节：具体文件、数据、函数、算法和失败处理。
4. 问题排查：现象、发现证据、影响、定位过程、修复和验证。
5. 效果：实验条件、指标、原始记录和结论边界。
6. 学习与协作：用真实经历说明能力变化和取舍过程。

每节采用“白话解释 → 具体例子 → 代码位置 → 面试追问 → 自己复述”。不必先背答案；卡住的地方就是下一轮需要补的知识。

项目能力可以据代码介绍；个人贡献、发现 bug 的经历和团队冲突只能据本人经历讲。仓库中的注释和提交记录不能证明是谁亲自完成了工作。若属于学习项目或在 AI 辅助下完成，就说明实际分工，并通过复现和改动积累可讲述的经历。

## 第 1 节：项目解决什么问题

一个用户要去杭州玩三天，希望去西湖、灵隐寺，偏好博物馆，住经济型酒店，并给出预算上限。用户希望拿到逐日景点、住宿、天气、费用及需要注意的缺失信息。

难点包括：搜索结果不一定对应正确地点；模型可能漏掉必去项；日期和天数可能不一致；同一景点可能重复安排；一天可能排不下；模型估算费用和未知费用容易混淆；外部调用慢或失败时仍要解释进度与结果。

当前系统有三块：

| 部分 | 负责的事 | 技术及其作用 |
|---|---|---|
| 网页 | 收集输入、展示进度、地图和费用、导出及社区入口 | Vue 3 + TypeScript，构建浏览器界面 |
| AI 后端 | 查数据、生成行程、验证、预算、缓存和后台任务 | FastAPI 提供 HTTP 接口；LangGraph 编排节点；模型处理语义与工具选择；高德提供地理和天气等数据；SQLite 保存本地记录 |
| 社区后端 | 发布行程、点赞、排行、社区热度 | Spring Boot 提供业务接口；MySQL 保存业务记录；Redis 处理去重、计数和排行 |

不是每次生成都会发布。发布是用户后续选择的动作。Java 社区热度可以作为下次规划的参考；模型使用效果还需要额外评测。

第一版口头介绍可用第三人称事实，不预先代入个人贡献：

> 这是一个旅行规划和行程分享项目。用户输入城市、日期、天数、必去景点和预算，系统会查询景点与天气，再生成逐日计划，并检查必去项、重复安排、时间估算和预算。Python 后端负责规划，Vue 负责展示，Java 后端负责发布、点赞和排行榜。项目还加入了费用三态，用来区分已知价格、估算价格和未知价格。当前 CP-SAT 排程是独立离线实验，线上仍由模型生成行程。

第一节验收：能不看稿说出用户输入、输出、三个部分的职责，以及一个最核心问题。先不要求记框架缩写或性能数字。

## 第 2 节：一次生成请求怎样走完

主图见 `backend/app/agents/graph.py`；接口与响应见 `backend/app/api/routes/trip.py`。

1. 前端提交请求；接口建立初始状态，统一确定天数、晚数和结束日期。异步入口返回任务 ID，后台继续执行。
2. `validate_city` 校验日期与容量、解析城市编码、解析必去景点；失败时不继续采集。城市编码 adcode 用于天气请求。
3. `collect_attractions` 与 `collect_weather` 并行采集。必去景点先进入候选池；天气按接口实际预报范围对齐，缺失日期留空并说明。
4. `compose_plan` 根据候选池和要求生成逐日 JSON。Pydantic 检查结构，代码再检查天数、日期、必去覆盖和候选依据。
5. `verify_plan` 检查重复景点、估算时长与地理跨度。有严重错误时反馈原因，按有界规则重试。
6. `resolve_hotel` 根据已经排入行程的景点选择酒店。选址依赖实际景点，因此安排在排程之后。
7. `patch_budget` 用代码计算费用；住宿按晚数，已知、估算和未知费用分开保存。
8. `verify_budget` 比较预算上限与费用信息。超限时按预算重试计数器决定是否重排，随后重新走验证、选酒店与算预算。
9. 响应出口综合数据降级、未解决校验项和预算结论，决定返回完整或部分结果，以及能否缓存。前端展示计划和提示。

学习时看数据如何变化：`request` 是用户输入；`attractions` 是候选池；`plan.days` 是实际安排；`hotel` 是住宿结果；`budget_verdict` 是预算结论。候选池不等于计划，每个节点也不都需要调用模型。

第二节追问：为什么先校验？为什么两路并行？为什么酒店后置？检查失败后到底修改哪份数据？

## 第 3 节：Agent 是怎样调用工具的

代码入口：`agents/attraction_agent.py`、`agents/react_loop.py`、`services/tools.py`、`services/amap.py`、`services/llm.py`。

以搜索景点为例：

1. 后端向模型提供城市、偏好、候选目标和允许使用的工具说明。
2. 模型返回工具调用，例如 `search_attractions` 及搜索参数。
3. 后端解析参数，检查该角色是否允许调用工具，执行 Python 函数。
4. 工具通过高德查数据，过滤与去重，完整实体存进 `ToolContext` 收集箱。
5. 工具返回摘要，后端按工具调用 ID 将结果加入对话历史，再请求模型。
6. 模型没有继续调用工具或达到步数上限时结束，节点从收集箱读取结构化实体。

模型不会自行执行 Python 函数；执行发生在服务端。工具调用给模型一个结构化的操作接口。原始实体与消息摘要分开，可以降低上下文开销，并保留外部数据依据。

同轮多个工具调用在当前代码中可以线程池并发执行；并发正确性仍取决于调用是否独立和共享收集箱更新方式，不能泛化为“任何工具都适合并行”。当前整体图是固定工作流，部分节点内部才由模型决定工具与步骤。

练习：用“模型提出操作 → 后端执行 → 返回结果 → 再决策”四步讲清 Agent。进一步追问为什么限制工具权限、步数，以及为什么存原始数据而只返回摘要。

## 第 4 节：验证和预算怎样落地

代码入口：`models/schemas.py`、`agents/planner_agent.py`、`agents/verify_plan.py`、`agents/budget.py`、`agents/verify_budget.py`。

结构正确：JSON 是否可解析、字段类型是否合理、日期与天数是否对齐。

用户约束：必去景点是否真的排入；计划是否引用候选实体。

计划复核：重复项、估算游览与通勤时间、地理跨度。通勤估计和直线跨度的检查提供启发式证据，不能证明真实道路下必然可执行。

外部事实回填：当前 `_enrich` 用候选 POI 坐标覆盖模型坐标，并回填门票金额及其状态，避免模型把“未知”改成“免费”。

费用项三态：known、estimated、unknown；未知金额为 null，列入未知项清单。已知与估算的小计不能被理解为包含未知费用的完整总成本。

预算例子：

| 输入 | 预算结论 |
|---|---|
| 上限 2500，已知费用 2600 | known_exceeded：已有充分超限证据 |
| 上限 2500，已知 1000，估算 1700 | estimated_exceeded：按估算超限，不能证明现实无解 |
| 上限 2500，已知和估算合计 1800，另有未知门票 | unverified：无法确认预算满足 |
| 上限 2500，合计 1800，没有未知项 | within：当前数据与估算口径内未超限 |
| 没有设置预算上限 | none：不判断预算约束 |

当前 `unverified` 会提示用户并阻止有预算约束的计划进入缓存，但不会仅因此把整份行程标为失败。必须分别读取计划交付状态和预算状态。已知或估算超限会参与最终不成功判定。

预算复核放在汇总之后，解决旧代码在预算尚未产生时就检查费用的问题。重试受计数器与图路由共同控制；理解时应跟踪具体数值变化，不能只依据注释断言恰好重排几次。

练习：未知门票与已知免费分别怎样表达？估算超支为什么不能叫真实无解？success=True 能否推导预算一定满足？

## 第 5 节：如何讲一个问题的排查

固定顺序：现象 → 怎么发现 → 影响 → 逐步定位 → 根因 → 修改 → 验证。

仓库记载的案例：酒店每晚 260 元、住 2 晚，但住宿合计为 0。这个问题请求正常返回，不会靠 HTTP 500 或异常日志自动暴露。

理解与复现的路线：

1. 用明确数据建立预期：260 × 2 = 520。
2. 确认酒店价格是否存在。
3. 检查预算节点实际读取的晚数。
4. 对照写入字段、`TripState` 声明和读取字段，看是否一致。
5. 项目记录的根因是一个未在状态中声明的晚数字段被丢弃；后续读取缺省 0，算出 0。
6. 当前代码统一读取 `state['nights']`。相关测试检查住宿按晚数，避免按天数或缺省零计算。

在本人复现前应说“项目记录里有这个问题，我理解其原因是……”。复现后才能讲自己如何构造输入、观察结果和验证修复。不要把建议的排查步骤冒充历史真实过程。

另可学习两个当前代码记录的案例：预检失败却沿普通天气边执行下游；预算检查先于预算汇总所以未触发。它们训练的是分支语义与数据依赖检查。

## 第 6 节：社区服务与并发追问

代码入口：`java-community/src/main/resources/lua/like.lua` 和 `java-community/src/main/java/com/trip/community/service/LikeService.java`。

点击点赞后，Java 调用 Redis Lua：限频、一人一赞、更新计数、更新 ZSET 排行。Redis 脚本把多步检查与写入放在一个原子执行过程里。`SADD` 返回是否新增，再决定是否递增，重复点赞不会再次增加计数。Lua 原子执行不能解释成“所有业务失败自动回滚”。

Java 另把成功记录放入进程内有界队列，每秒批量写 MySQL，插入去重并从流水重算计数。重复处理与幂等性有关；进程崩溃或队列满的可靠投递问题仍未解决。

Lua 也写入 `like:pending` 列表，但不能据此声称存在可靠消费：当前 Java 落库走自己的内存队列，需要检查恢复消费者是否实际存在。

压测指标应分清总用户数与同时并发数：README 的一次测试是 500 用户、并发度 128，记录约 QPS 456、p99 334ms。不能表述为 500 个请求始终同时执行，更不能把短时结果说成长期稳定承载量。

练习：为什么 SADD 和后续计数更新放同一脚本？Redis 成功但进程立即退出，会有什么影响？MySQL 为什么用流水重算？

## 第 7 节：效果、学习与贡献怎样表达

当前有三个不同层次的证据：

- 线上模型规划实验：`backend/experiments/summary.md` 和 `summary_v05.md`。压缩对照每组 3 次，记录总 token 中位数从 21755 到 13549，约下降 38%；它不能证明所有输入都提升，也不能直接说质量完全不变。
- 离线求解实验：`backend/spikes/tasks.json`、`results.csv`、`summary.md`。当前结果是 11 个任务，固定排期与 CP-SAT 两臂、各重复 3 次。没有模型调用，没有测试自然语言约束抽取，也没有接入线上主图。
- 单元测试：检查行为是否符合预期，与规划质量实验作用不同。README 和面试材料中的数量有版本差异，本次未重跑，不背一个未核实的最新数字。

CP-SAT 将结构化候选、必去要求、日时间窗及通勤矩阵转为变量与约束，搜索满足模型的排期。找到解、证明无解、未完成搜索是不同状态。这里时间可行和预算已验证也需要区分：结果里有 FEASIBLE 但预算 estimated_exceeded/unverified 的案例，不能统一声称全部任务预算满足。

学习能力的回答需要真实操作：学习前不理解什么 → 用什么文档/代码/实验学习 → 做出了什么 → 如何验证 → 现在知道哪些边界。例如亲自跑预算用例、画状态变化、改一个费用字段后观察结果，再形成自己的故事。

团队协作回答需要真实参与者与分歧。个人项目可明确说暂无真实团队冲突，讲需求澄清与技术取舍；不要虚构同事争论。若有实际冲突，说明共同目标、各方案的具体差异、用什么证据比较，以及如何落实决定。

## 陪练顺序

第 1 轮只练项目全貌：60 秒介绍，接着追问输入、输出和职责。

第 2 轮练主链路：从提交请求讲到返回计划，遇到错误时指出分支。

第 3 轮练 Agent 工具循环：能画消息、工具结果和原始数据的流向。

第 4 轮练验证与预算：用三个明确数值例子证明自己理解未知、估算与已知。

第 5 轮练排查：亲自复现一个可控制问题，保留输入、输出和验证记录。

第 6 轮按岗位深入：AI/Agent 岗重点讲工具、验证与评测；Java 后端岗重点讲点赞并发、幂等和持久化；全栈岗补异步任务、SSE、接口与前端状态。

每轮反馈只看四件事：事实是否准确、因果是否完整、是否具体到实现、能否回答一层追问。先讲清楚，再缩短表达。
