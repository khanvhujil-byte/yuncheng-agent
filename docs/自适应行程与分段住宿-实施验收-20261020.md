# 自适应行程与分段住宿：实施与验收记录

日期：2026-10-20。需求来源：`PRD-自适应行程与分段住宿-20261019.md`，用户已授权按 PRD 实施。

**结论：主要代码与交互已实现，离线契约和真实接口验收分开记录。真实复杂规划尚有失败，发布门槛 S05 尚未通过，不能作为全面上线验收通过。**

## 1. 已实现的行为

- 联合编排按入住日期选择酒店、景点与餐饮；市内连住和远郊分段均可表达，支持前一晚先住远郊。没有按“雪山”写死换酒店规则。
- v11 `stays` 是每晚住宿事实，含入住、退房、酒店、锁定状态和安排原因。连续段仅压缩模型输出，入库前展开，不能重复计费。旧 `hotel` 仅保留兼容摘要。
- 每天从前一晚酒店出发、在当晚酒店结束；首末日使用真实到离点，没有提供则明确未计接驳。换住预留60分钟。已核验入住窗口参与校验，不虚构寄存或营业事实。
- 远郊按坐标区域补采酒店、餐饮和行政区天气，保留“行政区参考/未知”状态，不拿市区天气冒充山地现场预报。编排可请求有限补采，不能执行模型任意 URL。
- 真实路线核算时优先长途；检查供应商明显不合理的距离/耗时并保留证据，失败有限重试。不通过修改交通方式、缩短游玩时长或放松公交可达性来通过验收。
- 房费逐晚计入对应日期；门票、实际安排餐饮及交通明细由代码汇总。内部无票价时走既有联网检索，再按既有授权的模型日常票价估算显示“未核验”，不当作官方报价。
- 住宿局部修改支持单晚、连续段、全部未锁定晚数；单晚变更重算当日和次日依赖，保留无关景点、餐厅及锁定住宿。版本、幂等、失败保留原计划沿用既有执行机制。
- 页面展示分段住宿、每天不同地图起终点、换住提醒、区域天气和按晚预算；住宿概览可直接修改该住宿段。
- 显式晚到早离按真实可用窗口派生餐次。22点到达日可以只入住，早离日只安排来得及的早餐；必去/主题约束仍须满足。
- 同一编排模型可有限修正餐次 ID。被拒绝的 ID 决策草稿只作为内部修复上下文，不能成为成功计划或覆盖有效版本，修复后重新绑定及复核。

### 尚未解决的发布阻碍

1. 复杂雪山/远郊规划仍会受模型候选选择、跨区域餐饮覆盖和路线额度耗尽影响；某轮通过不代表稳定通过。
2. 30天压力场景可完整展开住宿，但模型后续重排仍可能把29晚错误缩成1晚，或出现超长游玩日。代码拒绝错误，没有静默扩房或假报成功；该场景稳定性未验收通过。
3. 山区公共交通缺少可靠班次/接驳覆盖，现有高德结果不足时只能给出限制；铁路、长途客运、景区接驳的授权数据接入仍为PRD P1。
4. 没有获得普遍可靠的酒店营业/寄存信息；只有导入并有证据的窗口能作事实约束，不能承诺酒店提供未知服务。
5. 未完成冻结配置、相同供应商条件下的新旧性能p95对照，不能宣称达到性能提升目标。

因此：S01—S04、S06—S08已有实现和契约证据；S05的必测真实复杂用例和M5发布验收仍未闭环。不能将“能正确拒绝坏方案”说成“所有合理需求都能稳定生成”。

## 5. 参数与运行边界

- 能力开关：`ADAPTIVE_STAYS_ENABLED`，默认开启。旧单酒店路径保留。
- 区域：默认最多4个、共享12秒；住宿比较最多8次路线尝试、6秒，计入全程48次预算。
- 食品覆盖：默认最多5次，共享6秒；预编排最多1次，零覆盖/无早餐优先；不是无上限联网。
- 数据请求：每次最多2项，运行累计最多2项；餐次补丁最多12项；仍受原模型调用、token和运行时间限制。
- 路线：全程最多48次物理尝试，包含重试；先验证所选方案的长途，城市短途估算明确标识。异常供应商结果保留诊断但不进入共享实测缓存。
- 默认换住60分钟为产品预留，不是某酒店实测办理时间。预算按一人既有口径，不能冒充多人或实时订单报价。
