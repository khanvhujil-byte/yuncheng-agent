### P1-1 独立复核（verify_plan）的重试契约在默认路径上完全失效
- 位置（快照）：`backend/app/agents/graph.py:62-67`（`route_after_plan`）、`:108-109`（`route_after_experience`）；反证注释 `backend/app/agents/verify_plan.py:114-122`
- 现状复核：工作区 20:10 版本这两个函数**未改**，仍绕过。
- 问题：默认请求 `unified_planning=True, experience_enabled=True`，而 `composition_valid` 在 `node_timing.measured` 里等于“plan.days 非空”，即只要模型产出了任何一天就为 True。于是：
  - `route_after_plan` 第一条分支直接返回 `next` —— **verify_plan 写的 `validate_error` 在它自己的条件边上永远不会触发 `retry`**；
  - `route_after_experience` 同样直接 `next`，enrich 的体验错误也不会在 enrich 边上重排。
- 为什么是 bug：`verify_plan.py` 的注释与文档承诺“严重项写 validate_error → 借 compose_plan 的回喂重试机制再试一次（封顶 2 次）”，实现却把重试推迟到 `patch_budget → verify_budget` 之后的 `repair` 分支。后果：① 严重项（一天排不下 / 同一景点排两天）要先付完一整轮 enrich（真实路线查询、门票网页检索、预算汇总）才可能被修；② 这次 repair 与预算重排共享计数器（见 P1-5），把本可用于预算修复的轮次提前消耗掉；③ 若 `route_after_budget` 因 `available()` 已耗尽而返回 next，严重项只能以 success=False 的部分结果交付。
- 复现（离线，无需模型）：`probe_core.py` 探针 1，构造
  `{"unified_planning": True, "experience_enabled": True, "composition_valid": True, "validate_error": "同一景点…", "retries": 1, "planning_calls": 1, "planning_started_at": now, "usage": {}}`
  → 期望 `retry`，实际 `route_after_plan` 与 `route_after_experience` 都返回 `next`。
- 建议修法：`route_after_plan` 在返回 next 前先完整执行 `route_after_audit` 的判据（`validate_error` 且 `retries<2` 且 `available`），把“composition 有效”从判据里拿掉；`route_after_experience` 同理把 enrich 错误交给同一判据，而不是无条件 next。

### P1-5 comfort/selection repair 与预算重排共享 `budget_retries`，预算重排会被饿死（对 Lead 修法 A 的反例）
- 位置（快照）：`backend/app/agents/graph.py:99-107`；`backend/app/agents/verify_budget.py:45-49`
- 现状复核：工作区已把 `repair` 映射到 `prepare_budget_retry` 并加了 `budget_retries<2` 门槛（修法 A），但两类重排仍共用一个计数器 → 反例成立。
- 问题：`route_after_budget` 里非预算类 `validate_error` 优先返回 `repair`，repair 走 `prepare_budget_retry` 会把 `budget_retries+1`。于是两个 comfort/selection 修复轮之后，`budget_retries=2`；此时即使 `verify_budget` 判 `known_exceeded`（真正可修、且用户在意预算），路由直接 `next`，预算一次重排都拿不到。文档承诺的是“超预算最多进入 2 轮重排”，实际可能是 0 轮。
- 另外：`prepare_budget_retry` 每轮把 `retries` 重置为 0，所以每次 repair 又恢复 compose 内部 2 次尝试；整体仍受 `planning_max_calls=6`（`config.py:89`）与 180 秒上限兜底，不会真正死循环，但 6 次 compose 的额度会被 comfort 修复先吃掉。
- 复现：`probe_core.py` 探针 5：`budget_retries=2` + `budget_verdict.known_exceeded` → `route_after_budget` 返回 `next`；`budget_retries=1` + comfort `validate_error` → 返回 `repair`（继续消耗同一计数）。
- 建议修法：拆成两个计数器（`comfort_retries` / `budget_retries`），或 repair 只重置 `retries`、不递增 `budget_retries`；预算重排的条件改用 `budget_retries` 且保证至少 1 轮。

### P1-6 compose 的 LLM 错误/空候选路径会用空 plan 顶掉旧 plan，repair 轮里会丢掉已生成的行程（对 Lead 修法 B 的反例）

- 建议修法：见上；另建议在 repair 轮失败时保留 `previous_plan` 快照，`_finalize` 若发现本轮 plan 为空但上一版完整，则回退并如实 warning（“重排失败，已返回上一版”），这也是 12-Factor 的 fail-soft 口径。

- 状态：待验证（需 map 故障注入）；属于“降级未写 sources”的经典形态。
- 建议修法：只要有任一 `status != ok` 的 outcome 或 `ctx.errors` 里有 AMAP_* 错误，`sources.attractions` 写 `degraded`（或新增 `partial` 值并计入 `_degraded_sources`）。

### P2-5 旧缓存行缺 schedule/budget/sources 时存在复核盲区
- 位置：`backend/app/services/itinerary_experience.py:199-201`（`validate_experience` 对“没有 schedule 且 state 无 experience_enabled”直接 return []）；`backend/app/services/delivery.py:10-45`（`audit` 不检查 `budget` 是否存在、不检查天气占位字段是否为空）
