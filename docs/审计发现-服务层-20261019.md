## 0. 结论摘要

本次审计的两个“主结论”：

1. **缓存命中路径的“复核”是完整的（天气重取、日期平移、门票/住宿/餐饮价格重核、预算/约束重审都在），但复核失败后没有任何失效或回退机制**。一旦库里存在一份“当前复核不过”的条目，它会在 TTL（1 小时）内被反复命中、反复返回失败，并且没有“忽略缓存重新生成”的入口。这是本次最值得修的服务层缺陷（P1-1，已用脚本稳定复现）。
2. **任务状态外置做到了“重启后还能读”，但没做到“重启后能判定死亡”**。进程在生成中途被杀后，`job_state` 里留下 `status='running'`；新进程 `get_job` 原样恢复成 running，于是 `/plan/result` 永远返回“仍在生成中”、SSE 生成器无限循环占线程。这是“状态外置”的收尾缺口（P1-2，已复现）。

## 1. P1 缺陷（按建议修复优先级）

### P1-1 缓存命中复核失败后条目不失效、也不回退重算，坏结果持续供应到 TTL 结束

- 位置：
  - `backend/app/services/planning.py:343-408`（`_cached_response`：复核出 `ok=False`、写入 `run_log`、返回失败响应，全程没有删除/降级缓存条目）
  - `backend/app/services/planning.py:583-585`（命中即直接返回 `_cached_response`，没有“复核失败 → 继续走完整生成”的分支）
  - `backend/app/services/store.py:230-262`（`find_itinerary` 只做 TTL 判定并 `hit_count+1`；全项目搜不到任何 `DELETE FROM itinerary` / 失效接口）
- 问题：命中路径把复核结果如实写进了响应（`success=False`、message 里说“未通过校验”），但**没有把这条缓存标记为不可用**，也没有回退到完整生成。TTL 是 `ITINERARY_CACHE_TTL_SECONDS=3600`（`store.py:47`），且 TTL 只看生成时间、与请求日期无关。
- 后果：一份“当时合格、现在复核不过”的行程会被连续命中：用户拿不到可用行程，系统却不再消耗 LLM 去重新生成；同时 `hit_count` 与 `itineraries_reused` 继续增长，缓存指标看起来“复用很多”。触发条件不只是代码升级：命中路径会重新核价、重取天气、重跑 `verify_plan` / `verify_budget` / `audit_requirements` / `validate_experience`，任何一条外部条件或规则口径变化都会让老条目复核失败。
- 复现（已跑通，`_audit_verify_stale_cache.py`）：
  1. 临时库中给一个“3 天”的请求指纹存一份“只有 1 天”的行程；
  2. 只把 `planning._reuse_with_new_dates` 换成直通（复核逻辑全是真代码），连续调用 `planning.plan(req)`；
  3. 实测输出：3 次请求全部 `cached=True, success=False`，message 均为“days 数量是 1，但要求正好 3 天”；3 次后缓存条目仍在、`hit_count=3`、`run_log` 里 cached=1 三行。
- 建议修法（任一或组合）：
  - 命中复核失败时**删除该 fingerprint 的缓存行**（或写一个 `invalidated_at` 字段），随后按普通缓存 miss 走完整生成；
  - 或至少提供 `?refresh=1` / 请求头强制绕缓存，保证用户有自救入口；
  - 把“复核失败次数”记进缓存行，连续失败 N 次自动失效；
  - 注意与 `P2-1` 的 `hit_count` 口径一起改（失败命中不应计入“复用成功”）。

### P1-2 进程重启遗留 `status='running'` 任务没有回收，`/plan/result` 永远“仍在生成中”、SSE 生成器永不结束

- 位置：
  - `backend/app/services/runner.py:137-159`（`get_job`：内存没有就 `store.load_job` 原样恢复，**不校验租约、不判超时、不改状态**）
  - `backend/app/api/routes/trip.py:133-149`（SSE：`while True` 里只有 `done/error/None` 三个出口；`running` 时 `time.sleep(0.3)` 继续，**没有总超时、没有心跳超时、没有“执行者已消失”判定**）
  - `backend/app/api/routes/trip.py:158-168`（`/plan/result`：`status != "done"` 一律返回“仍在生成中”）
  - `backend/app/services/runner.py:210-215`（`_background_run` 的 `finally` 只释放租约；进程被强杀时 `job_state` 停在 running）
  - 对照：会话侧有 `dialog_store.recover_interrupted()`（`dialog_store.py:136-144`），**任务侧没有对应物**
- 问题：`job_state` 是“重启后仍能取到结果”的持久层（`runner.py:115-134`），但恢复时把“上次进程没写完的 running”当成“现在正在跑”。真正在跑的 run 一定在本进程 `_active_runs` 集合里（`get_job` 第 141 行才走内存分支）；从库里恢复出来的 running 一定没有执行者。
- 后果：重启前提交、重启时还没跑完的后台任务，前端 `/plan/stream` 会**永久保持连接**（每连接占用一个 anyio 线程池线程，见 P1-3）；轮询兜底 `/plan/result` 永久返回“仍在生成中”；任务永远不会被标记失败，也无法从该 thread_id 续跑得到新结果。前端的三级降级会一直停在最外层。
- 复现（已跑通，`_audit_verify_stale_job.py`）：临时库里写一条 `status='running'` 的 `job_state`（模拟上次进程被杀）→ `trip.plan_result()` 返回 `{'success': False, 'message': '仍在生成中', 'status': 'running'}`；`trip.plan_stream()` 的首帧正常回放历史节点事件，之后 2 秒内生成器不结束（实测超时）。
- 建议修法：
  - `get_job` 恢复 running 时检查 `execution_lease` 是否存在未过期的 `run:<thread_id>` 租约；不存在且 `updated_at` 超过 N 秒（或进程启动时间之后）→ 把状态改成 `error` 并写 `error="进程已重启，任务中断"`，或按 journal 标记“可续跑”；
  - SSE 增加“最长等待 / 心跳无更新超时 / 租约丢失即发 error 帧”；
  - 启动时做一次 `job_state` 对账（类似 `recover_interrupted`），把无租约的 running 置为 interrupted/error。
- 备注：现有 DB 实测 `job_state` 14 行全部 done、`execution_lease` 0 行，说明这条尚未在本地触发；但只要服务在生成中被杀过一次就会命中。

### P1-3 默认部署无鉴权、无限流，且全部端点（含 `/health`）共用同步线程池：约 40 个并发请求即可拖死整个服务

- 位置：
  - `backend/app/api/security.py:92-100`（限流默认关闭：`rate_limit_per_minute` 默认 0，`config.py:139`）
  - `backend/app/api/main.py:87-90`（只在“生产模式”强制限流；开发模式只打 warning）
  - `backend/app/api/routes/trip.py:49-122`（`/plan` 与 `/plan/async` 都是同步 def，同步 `graph.invoke` 一次几十秒；注释自己说明“用 def 时 FastAPI 会把它丢进线程池”）
  - `backend/app/api/routes/trip.py:133-155`（SSE 是同步生成器，同样占线程池线程，直到任务结束）
  - `backend/app/api/main.py:93-101`（`/health` 也是同步 def，与业务端点抢同一个线程池）
  - `backend/app/api/main.py:52-54`（`/api/ai/*` 无任何依赖）
- 问题：FastAPI/Starlette 对同步端点使用 anyio 默认线程池（容量 40）。本服务**没有任何 async def 端点**，所以 40 个慢请求（每个 `/plan` 几十秒、每个 SSE 连接整段生成期）会把线程池占满；后续 `/health`、`/metrics`、`/api/trip/stats` 全部排队。默认配置下不需要任何凭据就能发起这些请求。
- 后果：单机一台笔记本/一台小服务器即可被一个脚本打到“全站无响应”（健康检查也挂）；同时每个 `/plan` 都在花真实 LLM token（成本放大）。开发/演示环境（`docker-compose.yml`）与默认 `DEPLOYMENT_MODE=development` 都处于这个状态；`docker-compose.production.yml` 已通过 `RATE_LIMIT_PER_MINUTE=30` 和登录会话缓解，但 30/min 对 40 线程池而言余量仍薄（30 个并发慢请求即可占满）。
- 复现思路（建议 Lead 在黑盒中做）：对运行中的服务并发发 45 个 `POST /api/trip/plan`（可用“城市不存在”的请求，让每个请求至少阻塞在高德地理编码 10 秒，不烧 LLM），随后 `GET /health` 应出现明显排队/超时；也可并发 45 个 `/plan/stream/<不存在的 id>`？该路径快速返回，不能占线程，必须用真实慢请求。若使用有效请求则还会产生真实 token 消耗，建议不做。
- 建议修法：
  - `rate_limit_per_minute` 给出非零默认值（如开发 10/分钟），或在无 API_KEY 时也强制低配额；
  - 对昂贵端点（`/plan`、`/plan/async`、SSE）加进程内并发信号量（如 8），超限返回 429；
  - `/health`、`/metrics` 改成 `async def` 并保证不碰阻塞 IO，避免被业务拖死；
  - 生产模板把限流与 worker/线程池参数一起评估（`RATE_LIMIT_PER_MINUTE=30` 与 40 线程池不匹配）。
- 定性：这是本次唯一可被外部无凭据直接利用的“整体不可用”缺陷；按“上线可用性”口径可视为 P0 候选。

### P1-4 三个请求入口的字符串/列表没有长度与数量上限，最大可传数 MB 到数 GB 的字段

- 位置：
  - `backend/app/models/schemas.py:87-89`（`city: str`）、`:101-104`（`transportation` / `accommodation` / `preferences: List[str]` / `free_text_input: Optional[str]`）、`:108`（`must_visit`）、`:113-116`（`fixed_hotel` / `fixed_hotel_address`）——全部没有 `max_length` / 列表上限 / 元素长度上限
  - 对照：对话侧的 `SlotPatch` 反而有严格上限（`backend/app/models/dialog.py:8-27`：`Text` 200 字、preferences 20 个、free_text 2000 字），说明“输入严”只落在对话入口，表单入口没落
  - `backend/app/api/routes/community.py:32`（`PublishPayload.plan: dict[str, Any]` 无大小限制，原样转发给 Java）
  - `backend/app/api/routes/ai.py:36`（`SummaryRequest.plan_json: str` 无长度限制，且该端点无鉴权）
- 问题：校验层 `request_validation.validate_request`（`request_validation.py:9-53`）只查空、日期、晚数、必去数量，不查字符串长度。实测（`_audit_verify_services.py` [1]）`city` 2,000,002 字符、单个 preference 400,000 字符、`free_text_input` 2,000,000 字符、单个 must_visit 2,000 字符全部被 `TripRequest` 接受。
- 后果：
  - 这些字段会进入 `store.fingerprint_of`（JSON 序列化 + sha256）、`graph_run.request_json`、`run_snapshot.state_json`、prompt 组装（`planner_agent._build_user_prompt` 直接拼 `req.free_text_input` 等）、日志与 `run_log`，**prompt token 与磁盘占用随输入线性放大**；
  - 高德/DeepSeek 会先失败（参数过长、超时），最终以“模型不可用/城市解析失败”这类错误码返回，排障时很难看出是输入问题；
  - 伪造超长 `preferences`/`must_visit` 列表还可让容量预检、指纹计算、DB 写入做大量无用工作；
  - `SummaryRequest.plan_json` 在 `/api/ai/summary` 上被无鉴权接收并 `json.loads`（`ai.py:39-52`），是更廉价的放大面（生产靠 nginx `deploy/nginx.conf:14` 404 挡）。
- 复现：直接按上文字段构造请求 POST `/api/trip/plan`；观察日志里 prompt 长度、`graph_run.request_json` 大小、请求耗时。无需真实 Key 也可在本地观察到 `_reject_invalid_request` 通过（字段合法）后进入图。
- 建议修法：
  - 给 `TripRequest` 的每个字符串字段加 `Field(max_length=...)`（与 `SlotPatch` 对齐：城市 80、交通/住宿 80、偏好元素 200 且最多 20、必去元素 200 且最多 10、free_text 2000、固定酒店 200/500）；
  - `PublishPayload.plan` 加体积上限（如序列化后 512KB），`SummaryRequest.plan_json` 加 `max_length`（如 200KB）；
  - 若无反代，进程层再兜一层 body size（`client_max_body_size 2m` 目前只在 nginx）。

### P1-5 生成完成后的缓存/快照写库没有兜底：SQLite 一繁忙，成功的结果就变成 500 / 后台任务 error

- 位置：
  - `backend/app/services/planning.py:282-284`（`_finalize` 里直接 `store.save_itinerary(...)`，没有 try；这是“行程已生成、已花 LLM 费用之后”的那一步）
  - `backend/app/services/planning.py:583-585`（`plan()` 一开始 `store.find_itinerary(...)` 也没有兜底；DB 读失败会让**所有**请求 500）
  - `backend/app/services/store.py:144-153`（`sqlite3.connect(DB_PATH)` 未设置 `timeout`，用默认 5 秒；并发写/journal 高频写时可能 `database is locked`）
- 问题：可观测性写入有隔离（`delivery_logging.record` / `log_run` 都吞异常，`delivery_logging.py:7-19`），但**业务缓存写入没有**。`save_itinerary` 抛出的 `sqlite3.OperationalError` 在同步路径会一路冒到 FastAPI → 500；在后台路径被 `_execute` 的 `except Exception`（`runner.py:283-286`）捕获后 `job.status="error"`，用户同样拿不到已生成结果，且这份消耗无法通过重试恢复（要重新烧一次 token）。
- 后果：最常见失败方式是“最亏的一种”：40 秒 + 多个 LLM 调用全部白费，用户看到 500 或“任务执行失败”。SQLite 单文件 + 每个节点都写 journal（`runner.py:270`）+ 每事件都 `save_job`（`runner.py:162-165`）+ 同步端点在线程池并发 => 锁竞争是现实风险，不是理论风险。
- 复现思路：离线把 `store.DB_PATH` 指向一个只读目录或另一连接长期持有 `BEGIN EXCLUSIVE`，再调用 `_finalize`/`planning.plan` 命中省 token 路径；或并发压测 `/plan`（多个 bg 任务同时写 journal）观察 `journal_node`/`save_itinerary` 抛 `database is locked`。本次未做真实并发压测（审计约束不发起真实业务请求）。
- 建议修法：
  - `_finalize` 里把 `save_itinerary` 用 `delivery_logging` 同样的模式包一层：失败只记 warning + 结果照常返回（“结果可交付优先于缓存写入”）；
  - `_connect()` 显式 `timeout=30` 并配合 `PRAGMA busy_timeout`；写事务加统一重试（有限次）；
  - 考虑把 journal 写从“每节点两次落盘”收敛（`journal_node` 之后 `_emit` 又 `save_job`，一次节点等于两次写事务），降低锁窗口。

### P1-6 监控口径错误：`plan_success_rate` 把预检/输入失败算成“计划失败”，服务健康时会永久告警

- 位置：
  - `backend/app/services/monitoring.py:30-81`（`record` 记录每次运行的 success）
  - `backend/app/services/monitoring.py:106`（`plan_success = sum(r["success"] for r in reports) / len(reports)`）
  - `backend/app/services/monitoring.py:121-123`（`plan_success < 0.8` → `PLAN_FAILURE_RATE` 告警）
  - `backend/app/services/planning.py:245-257`（预检失败路径也 `_record_delivery(..., False, ...)`）、`planning.py:328-340`（`_reject_invalid_request` 同样写 success=False）
  - `backend/app/api/main.py:146-149`（`/metrics` 直接暴露 `trip_quality_plan_success_rate`）
- 问题：`CITY_NOT_FOUND` / `DATE_RANGE_MISMATCH` / `INVALID_REQUEST` / `CONSTRAINT_INFEASIBLE` / `CLARIFICATION_REQUIRED` 这些“用户输入不合法、系统按预期拦住”的运行，`run_log.success=0`、`quality_run.success=False`，却被当成“计划生成失败”统计。
- 后果：只要跑一批非法输入用例，`plan_success_rate` 会掉到接近 0，`summary()` 的 `status` 变成 `degraded`，`PLAN_FAILURE_RATE` 告警常亮——真正的生成失败会被淹没，`/metrics` 的“健康/降级”结论不可信。这会直接干扰 Lead 的黑盒评测结论（与“约束满足率/失败分类”交叉时尤其容易误判）。
- 复现（已用真实项目库只读复现）：直接调用 `monitoring.summary()`（只读 `quality_run`）→ 31 份报告、`plan_success_rate=0.0645`、`status=degraded`、alerts 含 `{"code":"PLAN_FAILURE_RATE","observed":0.935,"threshold":0.2}`；库中最近 `run_log` 大量是 `CITY_NOT_FOUND` / `DATE_RANGE_MISMATCH` / `INVALID_REQUEST`。黑盒侧只需：先跑 5 个以上非法输入场景，再 `GET /metrics` 看 `trip_quality_plan_success_rate`。
- 建议修法：区分“输入被拦”和“生成失败”。`run_log`/quality report 增加 `rejected=True` 或按 `error_code` 归类（预检错误码集合），`plan_success_rate` 只统计“通过预检、真正进入生成”的运行；`PLAN_FAILURE_RATE` 分母同口径。另建议暴露单独的 `input_rejected_rate`。
- 附带同类问题：`monitoring.py:102-105` 的 `INCOMPLETE_TOOL_TRACE` 会把历史报告里缺 `trace_warnings` 键的旧记录当成“trace 不完整”永久计数（实测库中 26 份报告有 5 份 legacy 缺该键，告警常亮），建议按“报告版本”过滤或迁移旧报告。

## 2. P2 缺陷

### P2-1 缓存与用量统计有四处口径污染，`/api/trip/stats` 与 `/metrics` 不能直接信

- `backend/app/services/planning.py:583-585`：`hit = store.find_itinerary(fingerprint)` 在 `if hit is not None and seed is None` **之前**执行。带 `seed` 的对话重排（`conversation.py:205-206`）并不使用这条缓存，但 `find_itinerary` 已经把 `hit_count+1`、`last_hit_at` 更新并打了“行程命中缓存”日志。
  实测（`_audit_verify_seedhit.py`）：响应 `cached=False`，但库里 `hit_count=1`、`stats.itineraries_reused=1`。
- `backend/app/services/store.py:438-441`：`llm_calls_generated` / `tokens_generated` 只对 `cached=0` 的行求和；而缓存命中路径会重新核价/搜票，`ticket_estimates.fill` 可能真的调用 LLM（`ticket_estimates.py:48-79`），`_cached_response` 也把这份 usage 记进了 `run_log`（`planning.py:384-390`）——只是被 stats 的 `CASE WHEN cached=0` 丢掉了。`/metrics` 的 token/call 总量因此系统性偏低。
- `backend/app/services/partial_edit.py:363-367`：局部修改以 `fingerprint="partial-edit:"+run_id`、`cached=False` 写 `run_log`。它会被算进 `total_runs`、`avg_ms_generated`、`cache_hit_rate` 的分母，但它既不是“生成请求”也不是“缓存命中”，`/api/trip/stats` 的“命中率/平均生成耗时”被污染。
- `backend/app/services/store.py:256-262`：`find_itinerary` 无条件 `hit_count+1`，即使调用方随后丢弃命中（seed 路径）或复核失败（P1-1）。`itineraries_reused` 因此是“被读到次数”，不是“成功复用次数”。
- 建议：把“缓存读取”和“命中消费”拆成两个函数（read 不写计数，commit 才写）；stats 增加 `cached_path_llm_calls` 或在 token 总计时不再按 cached 过滤；partial edit 用独立表/`run_kind` 字段标记。

### P2-2 同形状请求并发没有 in-flight 合并：重复生成、重复计费、缓存互相覆盖

- 位置：`backend/app/api/routes/trip.py:83-122`（异步入口先 `find_itinerary` 再 `start_job`；同步入口在 `planning.py:572-604` 同理）、`backend/app/services/runner.py:82-91`（互斥键是 `thread_id`，不是 fingerprint）
- 问题：两个用户/两个标签页同时提交同一形状请求（缓存 miss 的同一瞬间）会各自跑完整图；`_finalize` 最后都 `save_itinerary` 同一 fingerprint，后写覆盖先写（`store.py:200-223`）。既重复花 token/外部配额，也让“同形状请求只算一次”的缓存承诺在并发下失效。
- 建议：进程内按 fingerprint 做 in-flight 合并（`dict[fingerprint, Future]`），后到者 await 第一个结果；或至少让第二个请求在发现正在生成时返回“生成中 + thread_id 轮询”而不是另起一份。跨进程可用 `execution_lease` 的 `gen:<fingerprint>` 键。

### P2-3 `partial_edit.apply` 返回的新 thread_id 没有登记 owned_run / graph_run / job_state，三个按 thread_id 的端点对它表现为“未知任务”

- 位置：`backend/app/services/partial_edit.py:317-370`（新 `run_id` 只用于 `delivery_logging.record/log_run` 和响应 `thread_id`；没有 `owned_run` 插入、没有 `store.save_run`、没有 `job_state`）
- 对照：表单同步路径 `trip.py:62-70`、异步路径 `trip.py:90-97`、对话路径 `conversation.py:186-204` 都会写 `owned_run`
- 后果：局部修改成功后，响应里的 `thread_id`（新 run_id）在 `GET /api/trip/plan/result/<id>` 得到 `THREAD_GONE`、`GET /api/trip/journal/<id>` 得到空 journal、`POST /api/conversations/from-run` 得到 404“找不到属于当前用户的行程”。若前端在局部修改后继续用这个 thread_id 轮询/导入/续跑，会拿到“任务不存在”这类与“刚成功”矛盾的反馈（**待验证**：需确认前端是否消费该 thread_id；`test_partial_edit.py` 未覆盖这三个端点）。
- 建议：`partial_edit.apply` 落库时补齐 `owned_run`（`user_id` 可从 conversation 取）与 `graph_run`（或显式约定“局部修改结果不可用于 journal/result”，并在 `TripPlanResponse` 里不返回易误用的 thread_id / 增加 `resumable=false`）。

### P2-4 Docker 镜像绕过 `run.py` 的三层配置校验，错误 Key 不会 fail-fast

- 位置：`backend/Dockerfile:30`（`CMD ["uvicorn", "app.api.main:app", ...]` 直接起应用）、`backend/run.py:27-32`（只有 `run.py` 会 `setup_logging()` + `validate_config()`，后者包含“必需项非空、AMAP Key 格式、真实探测高德”三层）、`backend/app/api/main.py:82-90`（main 只做两条：生产模式缺 key 抛错、限流<=0 抛错）
- 后果：按文档用 `docker-compose.production.yml` 部署时不会执行 `validate_config()`；AMAP Key 填成错误类型/错误格式不会在启动时拦住，而是在第一个用户请求里以 `AMAP_KEY_INVALID` 暴露。文档/代码注释宣称的“三层校验”在生产路径上并不生效。
- 建议：把 `validate_config()` 的“必需项 + 格式”部分前移到 `main.py` 的模块级或 `lifespan` 启动阶段（探测高德可保留在 `run.py`）；或在 Dockerfile 的 entrypoint 里先跑一次轻量校验。

### P2-5 `/api/ai/*` 无鉴权、无限流，可直接消耗模型额度；安全性只依赖 nginx 与端口拓扑

- 位置：`backend/app/api/main.py:52-54`（注释明确“它不加鉴权与限流”）、`backend/app/api/routes/ai.py:65-94`（`/summary` 每次请求真正调用 `chat_text`）、`deploy/nginx.conf:14`（生产用 404 屏蔽）、`docker-compose.production.yml`（backend 未发布端口）
- 后果：在“直接 `python run.py` 或自行反代/移动端直连 8000”的部署形态下，任何人可无凭据、无限频地让服务调用 DeepSeek（虽然 `max_tokens=120`，但可刷量）；`plan_json` 无长度上限（同 P1-4）。当前仓库内的两套 compose 都没有把 8000 暴露到公网，所以定为 P2 而不是 P1。
- 建议：至少加一个共享密钥头（Java 侧配置同一个值）与一个低配额限流；或在服务内校验请求来源（仅容器网段）。

### P2-6 缓存命中路径仍有未做异常隔离的调用，DB/脏数据异常会直接把“命中”变成 500

- 位置：`backend/app/services/planning.py:493-496`（`Attraction.model_validate` + `apply_prices` 未包 try）、`:523`（餐饮 `apply_prices`）、`:539`（`Hotel.model_validate(data["hotel"])`）、`:554`（住宿 `apply_prices`）、`ticket_pricing.py:179` / `refresh_plan_tickets`（`cached_lookup` 的 sqlite 异常不在内层捕获）
- 对照：同函数里 geocode、catalog 读取、榜单读取都做了降级（`planning.py:441-446`、`:476-488`），说明“命中路径尽量不失败”是既定原则，只是漏了几处。
- 后果：缓存条目结构变化/价格表损坏/SQLite 短时不可用时，`/plan` 在命中分支 500；而命中分支正是“0 LLM、本该最稳”的路径。触发概率低，但一旦发生用户没有任何可用结果。
- 建议：把命中复核整体包进 `try/except Exception`，失败时按“缓存 miss + warning”处理（与 P1-1 的失效策略合并实现最省事）。

### P2-7 缓存命中路径会同步发起外部网页检索与官网抓取，单次可能 10~20 秒；`ticket_pricing._LOCK` 还把并发命中串行化

- 位置：`backend/app/services/planning.py:540-560`（命中路径调 `refresh_plan_tickets`）、`ticket_pricing.py:208-309`（内部 `_refresh_official` 抓官网 + `_search_batch` 抓 bing/sogou/政府页，预算 `ticket_web_budget_seconds=10` + 官网每源 4 秒）、`ticket_pricing.py:70-99`（`_load` 在模块级 `threading.RLock` 内做 `httpx.get(timeout=4)`）
- 后果：`/plan` 命中路径的耗时下限不是“毫秒级”，门票未核实的行程命中一次可能多花 10~20 秒；多个命中请求在 `_load` 的全局锁上排队，吞吐被串行化。这也会让缓存命中率的“平均 643ms”（实测库 `run_log` cached 行）与真实体验不一致——那张表里很多命中没有触发网页检索。
- 建议：命中路径的门票网页补查改为“异步/后台 + 下一次命中可见”，或设置更硬的整体超时（当前只有单次 HTTP 超时）；`_load` 把网络 I/O 移出全局锁（锁内只做 single-flight 占位）。

### P2-8 内存缓存无淘汰：`runner._jobs`、`java_bridge._hot_cache`、`security._hits`

- 位置：`backend/app/services/runner.py:67`（`_jobs` 全局 dict 只增不减）、`runner.py:157-158`（`get_job` 把从库里恢复的任务也塞回 `_jobs`）、`java_bridge.py:28`（`_hot_cache` 键含 `limit`，`/api/community/hot?limit=` 由用户控制）、`security.py:31`（`_hits` 按 client_key 累积 deque，旧 key 不清理）
- 后果：长期运行的单实例内存线性增长（每个 job 的 result 实测 26~54KB，加上事件列表；10000 次运行约 300~500MB）。`/community/hot` 只要登录用户不断变换 `limit` 就能塞进任意多份热度快照（每份是 deepcopy）。虽然生产限流能缓解，但这是“没有上限的缓存”，不是“有界缓存”。
- 建议：给 `_jobs` 加容量上限 + LRU/时间淘汰（只保留最近 N 个）；`_hot_cache` 对 limit 做 `min(max(1,limit),50)` 归一化；`_hits` 定期清理空 deque。

### P2-9 `trust_proxy_headers=True` 时无条件信任 `X-Forwarded-For`：后端端口一旦可达即可绕过限流与登录限频

- 位置：`backend/app/api/security.py:37-47`（`if forwarded and trust_proxy_headers: return forwarded.split(",")[0]`，没有“仅信任已知代理”校验）、`dialog.py:16-25`（`auth_limit` 也基于 `client_key`）、`docker-compose.production.yml`（`TRUST_PROXY_HEADERS: 'true'`）
- 问题/后果：所有限流键（包括登录爆破防护 `auth_limit` 10 次/分钟）都来自请求头。生产 compose 里 nginx 会用 `$remote_addr` 覆盖 XFF（`deploy/nginx.conf:31/50/58`），且 backend 不发布端口，所以当前拓扑下不可利用；但这条安全性完全依赖“没人能直连 8000 / 没人改 nginx 配置”。若运维把 backend 端口临时暴露（排查问题很常见），攻击者伪造 XFF 即可无限次尝试登录（每次仍要做 60 万次 PBKDF2，也可作为 CPU 放大）。
- 建议：`trust_proxy_headers` 之外增加“可信代理 CIDR”校验（只接受来自配置网段的请求头）；或改用 nginx 注入的独立共享密钥头标识可信代理。

### P2-10 鉴权/限流错误的响应体形状与业务错误不一致

- 位置：`backend/app/api/security.py:86-89`（401）、`:115-123`（429）把 `{success,message,error_code}` 放进 `HTTPException.detail`；`backend/app/services/identity.py:47/52` 直接 `HTTPException(401, "请先登录")`（纯字符串）；而业务错误是**顶层** `{success,error_code,message,...}`（如 `planning._finalize` 的响应）
- 后果：前端/Java 回调若按“顶层 error_code”统一解析，会在 401/429 时拿不到错误码；`detail` 里有时是 dict 有时是 str，形状不稳定。属于契约不一致，不是安全问题。
- 建议：统一用自定义异常处理器输出顶层结构；或在 OpenAPI/前端类型里显式声明 `ErrorEnvelope` 并同时兼容 `detail`。

### P2-11 对话层把非 LLM 的 `ValueError` 统一映射成 502“意图解析失败”；`reusable_seed` 对快照缺 `request` 的场景会 KeyError→500

- 位置：`backend/app/services/conversation.py:298-299`（`except (LlmError, LlmUnreachable, ValidationError, ValueError)` → 502 固定文案）、`conversation.py:104-121`（`reusable_seed` 里 `state["request"].model_dump()` 直接下标；`restore_state_types` 抛 `StateRestoreError(ValueError)`）
- 后果：`StateRestoreError`、深合并类型错误、`ValueError` 类业务异常都会被说成“意图解析失败，请重试”，排障方向误导；`run_snapshot` 若来自“预检失败的运行”（`_finalize` 的预检分支写入的 `final` 不含 `request`，`monitoring.py:80` 会照写快照）而被复用为 `previous`，`state["request"]` 会 KeyError（不在 except 列表里）→ 500。触发链较绕（需要会话结果指向一次预检失败运行），标**待验证**。
- 建议：`_turn` 的异常映射按类型细分（LLM 类→502，状态恢复类→409/422 并提示“请重新生成”）；`reusable_seed` 用 `.get("request")` 并显式判断，缺字段直接返回 None；`monitoring.record` 对无 `request` 的 final 不写 snapshot 或写 `request=None`。

### P2-12 `knowledge` 检索把所有文档全量载入内存并逐请求重建 bigram Counter（认证用户可放大）

- 位置：`backend/app/services/knowledge.py:41-88`（`SELECT *` 取用户全部未过期文档 → 每 500 字切块 → 每块算 `terms()` Counter → 每个查询变体再遍历全部块打分）、`dialog.py:174-179`（`/api/knowledge/search`）、`knowledge.py:34-38`（每用户最多 200 篇、单篇 100,000 字）
- 后果：单用户上限约 20MB 文本；一次检索要把 20MB 切块 + 建两套 token 计数 + 两轮打分，CPU/内存放大明显；同一用户反复调用即可让单 worker 变慢（且 pytest/CI 无真实负载测试覆盖这个量级）。
- 建议：入库时预先切块并落 `knowledge_chunk` 表（或至少缓存切块结果）；检索时先 SQL/`LIKE` 粗筛再打分；对单用户检索加并发/频率限制。

### P2-13 `catalog._connection` 每次调用都执行建表脚本与迁移检查，并持有进程级 RLock；资料库读写被串行化

- 位置：`backend/app/services/catalog.py:133-147`（每次 `_connection()` 都 `executescript(SCHEMA)` + `_migrate_index`，包在 `_SCHEMA_LOCK` 里）
- 后果：缓存命中路径与生成路径里的所有资料库读取/写入（`get_places_by_ids`、`rankings`、`search_places`、`upsert_places`、`ticket_web`/`price_catalog` 的缓存读写都走它）都在这把全局锁上排队；`_migrate_index` 还会在每次调用里做 `PRAGMA table_info`。单进程下这是可观测的吞吐上限。
- 建议：把建表/迁移放到 `init_db` 一次完成；`_connection` 只负责连接；读路径用独立只读连接；迁移用版本表而不是每次探测。

### P2-14 历史质量报告缺 `trace_warnings` 键导致 `INCOMPLETE_TOOL_TRACE` 永久告警（已实测命中）

- 位置：`backend/app/services/monitoring.py:102-105`（`sum(bool(r.get('trace_warnings')) for r in reports)`）、`monitoring.py:84-90`（读最近 200 份报告，不做版本过滤）
- 实测：项目库里 26 份 `quality_run` 有 5 份缺 `trace_warnings`；`monitoring.summary()` 的 alerts 里稳定出现 `{"code":"INCOMPLETE_TOOL_TRACE","observed":3}`（本次读到的值随 200 窗口取值变化）。
- 后果：只要旧报告还在窗口里，`status` 就一直是 `degraded`；一个“历史遗留”告警长期占位，和 P1-6 的假告警叠加，等于监控长期失效。
- 建议：报告写入时强制带全部键并在读取时用 `report.get("version")` 过滤旧版；或对 legacy 报告做一次迁移/回填。

### P2-15 数据卷与生产开关的文档/注释口径互相矛盾，按错口径运维会丢账号或配出不可用环境

- 位置：
  - `docker-compose.yml:12`、`:112`（“SQLite（生成缓存，可丢）”）与 `README.md:141`（同上）——但当前 SQLite 已含 `account` / `auth_session` / `conversation*` / `owned_run` / `knowledge_document` / 价格证据等（见 `store.py` SCHEMA 与 `dialog_store.py` SCHEMA），`docs/上线准备与验收-20261019.md:50` 也明确“绝不能再当作可丢缓存”。
  - `README.md:143-148`（“生产要显式打开的两个开关：API_KEY / RATE_LIMIT_PER_MINUTE”）——但 `security.py:60-65` 在 `DEPLOYMENT_MODE=production` 下**完全不校验 API_KEY**，改用登录会话；照 README 配 `API_KEY` 而用生产模板时它是被忽略的，照 README 把它当生产开关留在 development 模式时，前端不带 `X-API-Key`（`frontend/src/services/api.ts:77-78` 只有配了 `VITE_API_KEY` 才带）会导致业务接口全 401。
- 后果：最坏情况是按“可丢”注释清理/重建 `trip_data` 卷，账号、会话、会话版本、价格证据全部丢失；其次是生产开关配错导致接口全 401 或裸奔。
- 建议：统一以 `docs/上线准备与验收` 为准，改掉 `docker-compose.yml`/README 的“可丢”表述；README“生产开关”改成“生产用 `DEPLOYMENT_MODE=production` + 登录会话；`API_KEY` 仅用于 development 模式”。

### P2-16 `/plan/result` 与 `/plan/stream` 在“运行中/失败/成功”三种状态下返回不同字段形状

- 位置：`backend/app/api/routes/trip.py:158-168`（运行中：`{success,message,status,elapsed_ms}`；失败：`{success,message,status,error_code}`；成功：完整 `TripPlanResponse`）、`:133-149`（SSE `done` 的 `result` 是完整响应，`error` 帧是 `{type,message}`）
- 后果：前端需要三套分支解析；`success=False` 既可能表示“还在跑”也可能表示“失败”，只能靠 `status` 区分。契约本身缺少显式 discriminated union，容易在 UI 上加出“把生成中当失败”的 bug（README 里的三级降级依赖这些字段）。
- 建议：统一响应包装（如 `{status: running|done|error, result?: TripPlanResponse, error_code?: ...}`）并在 TS 类型里用 discriminated union 表达；错误码统一顶层。

### P2-17 进程被杀后 `execution_lease` 残留最多 120 秒，期间 `/plan/resume` 返回 `JOB_ALREADY_RUNNING`

- 位置：`backend/app/services/execution_lease.py:35-52`（租约 TTL 默认 120 秒，心跳 40 秒）、`runner.py:82-91`（`_claim_execution` 遇到未过期租约即 `JobAlreadyRunning`）、`trip.py:200-208`（映射成 `JOB_ALREADY_RUNNING`“任务正在执行”）
- 后果：进程崩溃/重启后，同一 thread 的续跑在 0~120 秒内会被自己的旧租约挡住，提示却是“任务正在执行”（误导，实际没有执行者）。会话侧 `recover_interrupted` 只处理会话，不处理执行租约。
- 建议：租约增加 `owner_pid`/`process_started_at`/`host` 字段，启动时清理“本机、pid 已不存在”的租约；或把续跑入口的错误文案改成“可能是一台已退出的执行者残留的租约，N 秒后可重试”。
