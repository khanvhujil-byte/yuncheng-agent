# CP-SAT 排程 spike（独立离线验证，未接入主图）

本目录是一个**离线、可复跑**的验证 spike，目的是在决定"要不要把排程接入主图"之前，
先把机制和证据摆出来。它**不调用任何模型、不接入 LangGraph 主图、不改动 `backend/app/` 下的任何文件**。

本 spike 的两臂是两个**求解/填充机制**，不是两种模型调用方式：

- **臂 A：固定排期基线** —— 确定性贪心顺序填充，不调用任何求解器；
- **臂 B：CP-SAT** —— 显式约束满足建模 + 求解。

两臂读**同一份** `tasks.json`、**同一套**约束、**同一个**独立打分器。

## 0. 先看结论范围（保证范围 guarantee scope）

脚本每次运行、`results.csv` 的每一行都会带上一句 `guarantee_scope`：

> 结论只在给定候选池、给定天/日时间窗、haversine 估算通勤（18.0 km/h 直线折算）
> 与估算/未知票价口径下成立；换候选池、换时间窗、换通勤估算或换票价数据，结论都可能改变。

换句话说：**这里证明的是"机制成立"，不是"真实行程可行"**。

### 约束抽取正确性不在本次测试范围内

这一点必须说清楚：本 spike 的约束（必去项、时间窗、每天上限、预算上限）是
**结构化约束输入**，直接写在 `tasks.json` 里，由脚本原样读入。

也就是说，"从用户自然语言里把约束抽对"这件事**完全没有被测试**。

## 2. 三种求解状态：FEASIBLE / INFEASIBLE / UNKNOWN

判定直接来自 `CpSolver.status()`：

| 求解器状态 | 本 spike 的判定 | 含义 |
|---|---|---|
| `OPTIMAL` / `FEASIBLE` | **FEASIBLE** | 找到满足全部约束的排期（`OPTIMAL` 同时说明已证最优） |
| `INFEASIBLE` | **INFEASIBLE** | 在**给定候选池、约束模型与估算数据**下确实无解 |
| `UNKNOWN` / 超时 / `MODEL_INVALID` | **UNKNOWN** | 搜索未完成或模型无效 —— **绝不当作无解** |

三条硬规矩：

1. **超时不算无解。** `UNKNOWN` 只表示"没算完"，不能读成"排不出来"。
2. **`INFEASIBLE` 不是"这趟旅行不可能"。** 它只对"这份候选池 + 这套约束 + 这套估算数据"成立。
   换一个候选池或放宽时间窗，同一趟旅行完全可能可行。
3. **建模自检失败也归 UNKNOWN。** 脚本在求解前调用 `model.Validate()`；
   自检不通过时判定降级为 `UNKNOWN` 并标明原因，避免把建模错误伪装成"无解"。

### INFEASIBLE 时怎么报"是哪些约束导致无解"

做法：把这四族约束（每天 POI 数量上限 / POI 开放时间窗 / 日窗口收起时刻 / 预算上限）
用**假设字面量**（`OnlyEnforceIf`）控制，并用 `AddAssumption` 登记，再调用
`SufficientAssumptionsForInfeasibility()` 取回一个子集。

报告口径（很重要，别读错）：

- 报出来的是**充分子集**：让这一组约束同时生效会导致无解；
- 组内**允许有冗余**，脚本会额外给出一个"精简后"的较小集合（逐条剔除得到）；
- **不声称是最小冲突集 / 最小不可约不可行子集（IIS）**。

脚本还给每条诊断附了可核查证据：

| 证据字段 | 怎么看 |
|---|---|
| `sufficiency_verified` | `True` = "只保留这一组约束、放开其余"实测仍无解，充分性成立 |
| `relaxation_status` | 上面那次实测的求解器状态 |
| `domain_infeasible_proof` | 纯计数就能证明无解时的领域下界说明（不必进搜索） |

实测：`T02` 报出 6 条、精简后是 1 条（"每天上限 <= 2"）；`T05` 报出 7 条、精简后是 1 条
（"净慈寺开放时间窗 11:05-11:55"）。

## 3. 预算口径：为什么不能只看一个 total

`known`（已知票价）与 `estimated`（估算票价）分别累加，`unknown`（`ticket_price = null`）
**绝不当 0**：它既不进"已知"，也不进"估算"，而是单独列为未核实项。

预算状态一共五种，含义各不相同：

| 状态 | 含义 | 不能拿它推导出什么 |
|---|---|---|
| `known_exceeded` | 已知费用就已超过上限 | 这个结论**不依赖**未知项，成立 |
| `estimated_exceeded` | 加入估算费用后超过上限 | **不能**据此断言"实际不可行"（估算不是实测） |
| `unverified` | 存在影响判断的未知项，无法核实 | **不能**按 0 元当作"通过" |
| `within` | 当前数据与估算口径内未超限 | 结论依赖 estimated 的准确性 |
| `none` | 用户没给上限 | 无法判断是否超支 |

未知项的**有依据的保守上界**：取同一个任务候选池中**最小的正票价**作为单个未知项的上界，
再按"所有未知项同时取到该上界"给出总上界估计。依据写在输出里
（`basis` 字段）：若真实总价超过该上界，则必然有一项已知/估算价格超过池内最小正价格，
与该价格是"最小"矛盾，所以这个上界不会低估真实总额。

**已知局限**：当候选池里除未知项外全是 0 元（没有正价格可作锚点）时，该上界退化为 0，
只能靠 `unverified` 状态本身提示风险。实测任务 `T09` 就是这个情况。

## 4. 两臂是什么、不是什么

### 臂 A：固定排期基线

- **是什么**：确定性贪心顺序填充。逐天从日窗口起点开始，按"必去优先（保持声明顺序）+ 其余按候选池顺序"
  尝试放入；满足日窗口、POI 开放窗、每天数量上限、预算硬约束（known + estimated）就放入，否则跳过。
  不含随机数，同样输入永远同样输出。
- **不是什么**：它**不是求解器**，不做回溯、不做交换、不搜索。
  - 它给出 `FEASIBLE` 只说明"贪心按这套规则排出来了"，**不能**推出"这个模型下一定有解"；
  - 它给出 `INFEASIBLE` 也只说明"贪心按这套规则排不出来"，**不能**推出"模型下无解"。
  - 实测中 `T04` 就出现了这个差异：贪心排不出来（判定 INFEASIBLE），CP-SAT 能排出来（FEASIBLE）。

### 臂 B：CP-SAT

- **是什么**：位置槽位建模 + 累积时间量 + `AddElement` 查表通勤 + 开放时间窗 + 每天上限
  + 必去覆盖 + 已知费用上限，目标分五层（多排 > 少花已知钱 > 少花估算钱 > 少走 > 早收工）。
- **不是什么**：它不解决"数据从哪来"。候选池、时间窗、票价、通勤速度全是输入，
  这些输入不对，CP-SAT 只会把错误数据"精确地"满足掉。

### 独立打分器

打分器**独立于求解器实现**（自己重算时间线、自己重算预算状态），两臂共用。它检查 9 项：

1. 天数一致；2. 无重复安排；3. POI 都在候选池内；4. `must_visit` 全覆盖；
5. 每天数量上限；6. 时间线（日窗口 + 通勤 + 开放窗）；7. 预算状态自洽；8. 未知项未被当作 0；
9. 已知费用未超上限（`known_exceeded` 不该被当成可接受行程）。

它在开发过程中确实抓到过建模 bug：
- "后一个槽位的开始时刻"漏掉了"前一个槽位的游览时长"，导致两次游览时间重叠；
- 求解器为了早收工把可选 POI 全部丢掉（目标权重层次设计错误）。

## 5. 约束模型（最小但要有意义）

每个 POI：`poi_id / name / visit_minutes / ticket_price(可为 null) / price_status(known|estimated|unknown) /
open_window(可选) / location(lng,lat)`。

任务级：`days`、`day_window(start,end)`、`must_visit[]`、`max_pois_per_day`、
`budget_limit(可选)`、`candidate_pool[]`（候选池）、`overrides`（任务级字段覆盖，可选）。

建模到代码里的约束：

- 每天起止时间窗；
- 每个 POI 的游览时长；
- POI 之间的通勤时间：**haversine 直线估算**，18 km/h 地面速度，按整分钟取整，单程下限 1 分钟。
  输出里一律标 `estimated`（`travel_time_status` 字段），它不是路网真实时间；
- `must_visit` 必须被安排，且整个行程内每个 POI 最多安排一次；
- 每天 POI 数量上限；
- POI 开放时间窗（若给定）必须完整容纳"进入-离开"区间；
- 预算：`known` 累加、`estimated` 单独累加、`unknown` 不进预算硬约束（见第 3 节）。

`visit_minutes` 也是人工设定值，同样是 `estimated`，不是实测。

## 6. 11 个任务覆盖了什么

| 任务 | 覆盖点 | 预期（写在 `expect` 字段里，供人审查，未硬编码进求解逻辑） |
|---|---|---|
| `T01_relaxed_feasible` | 宽松可行 | FEASIBLE，但候选池有未知票价 -> `unverified` |
| `T02_capacity_style_infeasible` | 计数型无解 | INFEASIBLE：必去 3 > 天数 1 x 上限 2 |
| `T03_unknown_cost` | 未知费用 | FEASIBLE + `unverified`，未知项不按 0 通过 |
| `T04_tight_window_feasible` | 边界时间窗（刚好卡住） | FEASIBLE：净慈寺 10:55-11:55，游览 55 分钟正好填满 |
| `T05_five_minutes_short` | 边界时间窗（差一点） | INFEASIBLE：窗口 11:05-11:55 只有 50 分钟，装不下 55 分钟游览 |
| `T06_cross_day_split` | 需要跨天 | FEASIBLE：西溪 150 分钟 + 良渚 180 分钟必须分两天 |
| `T07_two_must_one_slot` | 每天上限 1 的跨天 | FEASIBLE：一人一天 |
| `T08_budget_tight` | 预算紧张 | FEASIBLE + `estimated_exceeded`：known 115 未超 140，加上 estimated 110 才超 |
| `T09_budget_unverified` | 未知项影响预算判断 | FEASIBLE + `unverified`（池内无正价格，上界退化） |
| `T10_unknown_bound_trips` | 未知项上界触顶 | FEASIBLE + `unverified` |
| `T11_known_price_over_budget` | 确定超支 | CP-SAT 判 INFEASIBLE（known 115 > 上限 100）；基线不判这个 |

注意 `T04` / `T05` 是**同一个 POI（净慈寺）的两个不同开放窗**，用 `overrides` 在同一任务里改窗口，
这样两题除了窗口早/晚 10 分钟之外完全同构。

### 两臂的实际差异（实测，只有 3 处）

| 任务 | 固定排期基线 | CP-SAT | 差异性质 |
|---|---|---|---|
| `T04_tight_window_feasible` | INFEASIBLE | FEASIBLE | **基线漏解**：贪心不回溯，排进雷峰塔后放不下净慈寺；CP-SAT 能找到"净慈寺先排"的解 |
| `T11_known_price_over_budget` | FEASIBLE（`known_exceeded`） | INFEASIBLE | **基线不判预算**：它只做可行性判断；CP-SAT 把"已知费用超限"当硬约束 |
| 其余 9 个任务 | 判定一致 | 判定一致 | 一致 |

这两处差异都是**刻意保留**的，正好用来说明"基线不是求解器"和"预算在模型里怎么处理"。

### 预算口径与"预算该不该当硬约束"

本 spike 最终选择的处理方式是：

- **已知费用（known）超限 -> 硬约束拒绝**。这是确定的超支，无论未知项如何都成立，
  所以 CP-SAT 会判 `INFEASIBLE`（`T11` 就是这个例子）。
- **估算费用（estimated）超限 -> 不否决排期**，只在目标函数里做"尽量少花"的偏好，
  预算结论由 `estimated_exceeded` 单独表达。
  原因：`estimated` 不是实测值，用它去否决一个真实可行的行程，等于把估算误差当成事实。
- **未知费用（unknown）-> 完全不进预算判断**，只在结论里标 `unverified`。

固定排期基线**不拿预算当硬条件**（它只做"排得下/排不下"的可行性判断），
所以 `T11` 上两臂判定不同 —— 这是刻意暴露基线的能力边界，不是 bug。

## 7. 已知局限与现在还不能下的结论

1. **不能外推。** 只有 11 个任务、每任务 3 次重复，样本很小；这些数字只说明机制在这套数据上的表现。
2. **约束抽取正确性未测**（见第 0 节）。
3. **通勤是直线估算**，不是路网时间；真实通勤更长时，"刚好卡住"的边界题结论可能翻转。
4. **票价是人工数据**，`estimated` 值不是实测值；`estimated_exceeded` 不等于实际超支。
5. **没测真实行程质量**。本 spike 只验证"约束满足 + 状态语义 + 预算口径"，
   没有评价行程是否好玩、是否合理。
6. **本 spike 不代表已经可以接入主图。** 它只说明机制可行、语义清楚；
   接入还需要解决：约束从哪来（抽取与校验）、候选池规模变大后的求解时间、
   与现有 `compose_plan` 重试链路的职责划分。
7. **超时行为只在很小的模型上测过**。11 个任务都在 5 秒内解完（实测单次 <= 0.2 秒），
   所以 `UNKNOWN` 这条分支**没有被真实触发过**——脚本支持它，但缺乏真实证据。
8. **"候选池该多大"没有结论。** 本 spike 每任务只有 4-6 个候选，是刻意压小以便快速验证。
   真实场景几十上百个 POI 时，求解时间、目标权重、诊断耗时都需要重新验证。
9. **目标函数的层次是人为定的**（多排 > 少花已知钱 > 少花估算钱 > 少走 > 早收工）。
   换一套层次会得到不同的"最优"行程；哪套更符合产品目标，本 spike 回答不了。

## 8. 开发过程中踩到的坑（都值得记住）

**建模/求解类的 6 个：**

1. **`OnlyEnforceIf(literal)` 是"削弱"不是"加强"。** 字面量自由时默认取假，
   约束等于不存在。只写假设版本、又忘了把字面量固定为真 = 约束全部失效，
   结果不可行的任务被判成 FEASIBLE。
2. **`AddAssumption` 会强制字面量为真。** 诊断时想"放开某条约束"必须
   **在假设列表里去掉它**（诊断模型干脆不登记假设），不能简单 `Add(lit == 0)`——
   那会和"假定为真"直接矛盾，永远解不开。这个坑让诊断结果先假了整整一轮。
3. **通勤约束容易漏掉"前一个槽位的游览时长"。** 写成
   `t[s] >= t[s-1] + travel` 会让两次游览时间重叠；正确写法是
   `t[s] >= t[s-1] + visit[s-1] + travel`。这个是独立打分器抓出来的。
4. **目标函数的权重层次必须按"累积量"的量级设计。** 一开始把"少走路"的权重
   设得比"多排一处"大，求解器为了减少通勤和收工时刻，把可选 POI 全丢掉了，
   甚至把两处景点拆到两天。权重必须保证"多排一处"压得过一整天的收工时刻变化。
5. **CP-SAT 线性表达式不接受浮点系数。** 票价先乘 100 转整数（分），预算上限同比放大。
6. **"加一份硬约束副本"会毁掉诊断。** 一度为了让语义直观，在假设字面量之外
   又加了一份硬约束；结果"放开假设"后约束依然生效，模型永远解不开，
   诊断无法自查。正确做法是：约束只由字面量控制，正常求解时统一把字面量固定为真。

**检查/清理类的 2 个（检查本身写错，比没有检查更糟）：**

7. **一致性检查把"臂间差异"当成"重复不稳定"。** 第一版直接对同一任务的两臂全部重复
   取 verdict 集合，于是 `--reps 1` 时 `T11` 会打出
   "重复 1 次判定不一致 -> ['FEASIBLE','INFEASIBLE']" —— 那其实是
   基线 FEASIBLE / CP-SAT INFEASIBLE 的**设计差异**（见第 6 节）。
   已改为**按臂分别**比较重复结果，臂间差异单独打印成
   "臂间差异（设计差异，非重复不稳定）"。
   已验证：把某次重复的判定人为改掉后，"同一臂内重复不稳定"的警告仍能正确触发。
8. **`solve_cpsat` 里重复解包了 6 个它不用的名字。** `travel_used` / `day_last_end` /
   `travel_table` / `windows` / `day_start` / `day_end` 被 ruff 的 F841 抓出来。
   逐个核对后确认：它们**都在 `build_model` 内部就已经用掉了**
   （通勤表用于 `AddElement`，`travel_used` 与 `day_last_end` 用于目标函数），
   不是"该用没用"，所以只删掉外层这 6 行解包，建模逻辑一行未动。
